# 動画と解説記事の制作ノウハウ

更新日：2026-10-31。制作を進める本人と、引き継ぎを受ける担当者向けの総覧。企画、人物、実演、音声、編集、記事、レビューを一つの案件として扱い、少ない確認と部分修正で品質を上げる。

制作の入口はこのチャットとする。助手が調査・構成・記録を用意し、ユーザーは伝えたいことと採否を返す。Studioへの入力や素材の探し直しをユーザーの前提作業にしない。

## 0 チャットをまたいで参照し 更新する

制作記録は、[索引](README.md)、この総覧、各案件の `RESUME_AND_KNOWHOW_JA.md` の3種類を入口に管理する。専門別冊は工程の詳細、旧制作記録・JSON・プロンプトは証拠として残し、全内容を3種類へ複製しない。案件一覧と専門資料は索引から探す。

新しいチャット・再開時には、索引→総覧→対象案件の再開記録を実際に読み、必要な詳細根拠へ進む。参照資料、対象版、採用済み事項、次の作業を短く報告してから着手する。新規案件は [制作記録ひな形](templates/PRODUCTION_RECORD_JA.md) を案件内の `RESUME_AND_KNOWHOW_JA.md` として作成し、索引へ追加する。記入は助手の仕事とする。

| 更新の機会 | 更新する内容 |
| --- | --- |
| 再開 | コード・素材・実行環境の所在、採用版と候補版、残作業を根拠記録と照合 |
| 調査・構成・素材・声・編集の変更 | 依頼原文または必要な要約、対象版、判断と理由、影響する動画場面・記事節 |
| 生成・検査・レビュー・採用 | 初回と修正、再利用、実施した検査、返答の対象と範囲、未確認の状態 |
| 終了・引き継ぎ | 最新の現在地、次の具体的な作業と完了根拠、素材・出典・版への参照、Git同期状況 |
| 共通化できる学び | 案件の問題→対応→結果→適用条件をこの総覧へ反映し、工程別の詳細へリンク |
| 案件・資料の追加や移動 | 索引と参照元を更新し、リンク先を確認 |

再開記録の先頭は最新の判断へ更新し、履歴表は日付・版付きで追記する。訂正時は旧判断と訂正根拠を残す。既存の未完了依頼を消したり、技術検査を採用・公開へ読み替えたりしない。別案件へ適用できるか未検証の学びは仮説とする。無関係な全成果物を作り直さない。

制作の進行状態・素材hash・承認範囲の機械可読台帳は引き続き照合する。再開記録は人が判断を復元するための入口で、台帳の安全制御を置き換えない。食い違いがあれば対象版と根拠を確認し、不一致を残して依存する作業を止める。

3種類はGitで共有できる軽量な文書とし、一時的なworktree絶対パスや署名URLを正本の住所にしない。cloneでは原本・音声・動画が付属しないため、素材の所在とhashを別に確認する。文書を置いたことは読了の保証ではない。新しいチャットから実際に次の作業を復元できるかを確認する。

## 1 伝える結果を先に決める

最初に「誰が、何に困り、見終えると何が分かるか」を一文にする。機能名を列挙する前に、作業と結果、従来との違い、必要な人の判断を定める。例えばDocsなら、文書が出力できることだけでなく、資料を参照し、人とAIが下書きを修正・確認できる価値を説明する。

公式発表・ヘルプ・変更履歴から幅広く調べ、提供日、対象プラン・地域、制約、出典と確認日を残す。助手が推奨本数と理由、各回の結論・概要・実演・記事の役割を提案し、ユーザーの意図を受けて採用する版を記録する。最初からシリーズ全話を量産しない。

| 工程 | 次へ進むためにそろえるもの |
| --- | --- |
| 調査と企画 | 伝える一文、本数と各回の概要、公式根拠、ユーザーの返答と反映方針 |
| 撮影可否の確認 | ユーザーPCの実画面、機能の入口、保存と可読性。撮れない場合は試した経路と理由 |
| 人物と構成 | 確認済みの人物・ペルソナ、役割、カット割り、台詞、必要な証拠 |
| 素材と音声 | 実演原本、公式引用、人物動画、記事用画像、読み原稿、場面別音声 |
| 初稿 | まず1本の動画、投稿見出し、記事草稿、素材一覧 |
| 修正 | 指摘時刻、対象版、変更した素材、影響する場面と記事節、再確認結果 |
| 共有と採用 | Driveの対象版、確認してほしい2〜3点、試聴・採用・公開の個別状態 |
| 資産化 | 台本、出典、プロンプト、人物設定、改善理由、検証要約と最新版への参照 |

規定や確認待ちと、実装済みの機能を分ける。企画の準備が整っても、撮影成功、最終試聴、完成物採用、公開の完了には置き換えない。

## 2 題名と冒頭で見る理由を伝える

投稿タイトルの基本形は `【製品名】具体的な作業・得られる結果`。dots編は `【ChatGPT】`、ほかは主役に合わせて `【Codex】`、`【Claude】` 等を選ぶ。例は `【ChatGPT】Excelからシステムへ自動転記！dotsの実演と人の確認`。

投稿タイトルは動画の約束、冒頭見出しは音を出す前の題材説明、サムネイルは小さく見ても分かる主題、記事題は詳しく読める手順と前提を担う。同じ長文を全箇所へ貼らない。未検証の時短率、ミスゼロ、永久保存などを見出しで約束しない。

短尺は完成物・得られる状態を先に示し、操作、結果の確認、注意点へ進む。dots追加編の「冒頭1〜2秒、1本1用途・20〜35秒、まず2〜3本」は試作方針であり、短ければ伸びると実証した数値ではない。

フル動画は、完成像・題材、人物の目的と疑問、製品や作業場所の前提、実演、照合、注意点と次の行動の順で組む。人物の待ち合わせを入れる場合も、冒頭に短い題材見出しを置く。会話から未知のGUIへ切り替える前に、起動画面などで「何か・どこで・何を頼めるか」を一つそろえる。

## 3 人物を案内役として育てる

新シリーズでは架空の成人の人物とペルソナを先に作る。顔・全身・衣装・役割をユーザーへ示し、明示された採用範囲を記録してから本番の人物動画へ進む。知的で親しみやすい仕事の人物を基準にし、過度なポーズや見た目を人物の個性の代わりにしない。

シリーズ内では顔、体格、衣装、配色、左右位置、仕事、性格、口調、相方との関係を維持する。物語は「困る・疑問を持つ → 試す → 気づく → 行動する → 結果を確認する」。回ごとに課題と動作を変え、同じ静止画と文章だけの繰り返しを避ける。

dots詳細編では男性が質問役、女性が実務・解説役で、女性が答えながら進める。質問は次の操作や判断を引き出し、相づちだけで尺を埋めない。この役割を他シリーズへ性別だけで固定しない。

| 場面 | 人物の使い方 |
| --- | --- |
| 登場、困りごと、ひらめき | 大きく、必要なら全面表示。題材見出しと顔・手を分離 |
| 実演前、要点、注意、締め | 左右PIP。誰を出すか、区間と表示理由を記録 |
| 入力、登録クリック、金額や日付の照合 | 操作と証拠の画面を優先し、邪魔になるPIPは隠す |

話者は話し、聞き手は閉口して反応する。PCM音声の強度に応じた口の開閉は「簡易口パク」と記録し、音素同期した人物動画とは区別する。MiniMaxの動画、表情アトラスの編集、実演映像の来歴を混ぜない。

## 4 人物動画の動きと生成時間を設計する

採用済みの参照画像を基準に、MiniMaxで人物を動かす。動作は開始・中盤・終わりまで配分し、視線、表情、手、姿勢、移動方向、カメラの動きを具体化する。開始・終了フレームを使う場合は、衣装、位置、人数、画角を両端でそろえる。

参照原本とモデル投入用の画像を分け、アスペクト比と実寸を先に合わせる。引き伸ばしによる顔や体の変形を防ぐ。生成前に静止画の顔、手、衣装、背景を確認すると、動画を何度も作り直す手間を減らせる。

短いカットへ分割すると、動作の失敗を切り離し、採用した素材だけを再利用しやすい。動作が早く終わって静止に近くなる問題は、後半にも目的のある動きを割り当てて直す。静止画のズームや動画の引き伸ばしだけで人物が演技したとは扱わない。

低VRAMでの所要時間は、samplingだけでなく、offloadやVideo-VAEなど後段も計測する。過去には5秒素材の総生成時間が数時間になった例があるが、現在の全モデル・全設定の速度を示すものではない。[ローカル制作プレイブック](../../PRODUCTION_PLAYBOOK_JA.md) に条件と実測を残す。

外部APIは、画質・動き・待ち時間を改善する候補として比較する。2026-10-28の[候補調査](research/EXTERNAL_VIDEO_API_20261028.json)は調査段階の記録で、モデルの採用や実品質比較の成功を意味しない。現在の料金・利用可否は実行時に確認する。

比較では、同じ人物・動作・目標尺を用意し、解像度、量子化、入力素材、乱数、音声、native生成とアップスケールの違いを記録する。キュー待ち込みの完了時間、顔と手の安定、動作の継続、採用率、再生成を含む採用1カット当たり費用で判断する。動き量だけで品質順位を決めない。

## 5 実画面で証明し 図で関係を伝える

台本や代替画像を固める前に、ユーザーPCで対象機能を開き、ログイン済み環境、入口、実表示、保存、文字の読みやすさを調べる。既存画像があることだけで追加撮影を省略しない。URLや対象画面を安全に確認できなければ、そこで停止した理由を残し、撮影済みへ置き換えない。

契約プランや使用状況のニュースでは、画面の読取確認、個人の増量の前後比較、同条件での消費量実験を分ける。残量パーセントを見ただけで枠の倍増を実証したとしない。架空データを入力していない設定画面の観察を、架空素材の実演として登録しない。実演専用の台帳項目へ合わせるためにfictionalフラグを偽らず、原素材と観察記録へ保存する。個人情報・請求情報・実残量を除く切り出しを候補にし、プラン変更・購入・リセットは撮影のために実行しない。実例は [Pro利用枠ニュース](../../productions/content-projects/CONTENT_20261030_chatgpt_pro_usage_news/RESUME_AND_KNOWHOW_JA.md)。

2026-10-31の同案件では、ユーザー指定の伸びるグラフを、各対象プランの従来枠＝1とする相対表示にした。異なるプランの絶対量、具体的な回数・時間、実際の使用量、完了仕事数へ読み替えない。倍率だけが根拠のときに固定値を創作せず、絶対量の非公表を全資料について網羅確認したとも書かない。成長途中と最大値を実MP4で点検し、数値の上の見出しと十分な余白を取る。v01の近接をv02で修正し、音声は再利用した。

実演は架空素材を使い、入力前、初回出力、修正依頼、修正後、確認・保存の違いを撮る。AIが結果を指摘したこと、制作側が修正したこと、アプリを自動操作したことは別の実証である。人物の会話で本人の実際の許可を代用しない。

原本を保持し、動画用の切り出しと記事用の画像を分ける。記事本文の表示幅が700pxなら原本幅約1400pxを目安にするが、実際の読みやすさを優先する。小さい画像を拡大しただけで高解像度撮影済みとはしない。拡張子と実際の画像形式も確認し、JPEGをPNGへ変換しても細部が回復したとは説明しない。

金額・日付・IDを読む場面では、カーソルや選択範囲が桁を隠さないか確認する。隠れる場合は読める実フレームを選ぶか再撮影する。数字やUIを生成・画像編集で書き直して実画面として見せない。XLSXを専用ビューアで見せた場合は、Microsoft Excel本体の画面とは呼ばない。

公式資料は、掲載ページ、取得元、確認日、引用箇所、利用条件を保存する。動画の該当場面と説明欄・記事から出典をたどれるようにする。出典を書くことだけで全画像の利用を許可されたとは扱わない。

仕組みの図は、利用者、サーバー、そこで動く機能などの役割と境界、情報の流れを示す。身近な具体例から仕組みへ進み、視聴者が確認・行動することへ戻す。例えば「サイトを見る人 → サーバー内のPHPとサービス → 画面への応答」を、WordPressやフォームの利用と結ぶ。文字を箱へ入れるだけで図解したことにしない。

## 6 声を固定し 台詞と画面の尺を合わせる

基本の声はユーザーが選んだGemini Aoede、Koreは比較候補。dots詳細編の2話者は女性Aoede、男性Charon。原稿・声・速度の方針と対象版をそろえてから生成する。過去に使ったモデルIDや料金を恒久的な利用条件として固定しない。

表示原稿と読み原稿を分離し、少し速めでも明瞭な標準日本語にする。`story.rate` の数値だけで全APIの発話速度が同じ倍率になるとは説明しない。原稿の短文化、句切り、生成指示、短い試聴で調整する。

| 表示する語句 | 読みの指定例 |
| --- | --- |
| dots | ドッツ |
| Excel | エクセル |
| 元の表 | 元のひょう |
| Fable5.1 | フェイブルごーてんいち |
| Fable5 | フェイブルファイブ |

長い語から対象語句単位で置換する。「表」の一括置換で「表示」を壊さず、読み仮名で表示字幕を上書きしない。生成には引用した台詞だけを読ませ、質問文への回答や、話者名、あいさつ、音楽を追加させない。

台詞ごとに生成してPCMの実尺で配置する。質問の直後は返答へつなぎ、画面を読む間は説明の後に置く。過去の0.35秒の返答間隔は個別の会話設定であり、一律の規則にしない。長い発話を途中で切って収めず、文章か場面尺を直す。

原稿、声、モデル、発音辞書、音声のhashが一致する検証済み素材は再利用する。映像だけの変更では追加TTSを避け、可能なら旧AACを再圧縮せずコピーして一致を確かめる。原本、修正分、累計の生成回数と費用を分ける。

APIキーは環境変数等で扱い、資料やログに出さない。Windowsのユーザー環境変数を変更しても古いプロセスには反映されないことがあるため、値を表示せず設定の有無と読込み元を確かめる。拒否や結果不明の送信記録を消して自動再送しない。音声が生成できない場合は、字幕・BGM付き初稿とナレーション完成版を区別する。

## 7 音楽と字幕で理解を助ける

BGMは声と別に管理し、話している間は減音する。明るい曲調と大きな音量を混同しない。dots詳細編には112 BPM・Cメジャーの明るい伴奏を採用した例があり、全動画の固定設定にはしない。生成した各人物カットの音をつなぎ合わせず、一本の動画として声・BGM・効果音を整える。

字幕は短い意味のまとまりで区切り、見出しは結論、音声は理由や条件を担う。「専用ビューアで表示」を「表／示」に分断しない。はみ出すときは、まず文言と改行を直し、読めない大きさまで縮めない。

1080px幅の縦型テンプレートには主要文字54px以上、字幕66pxの制作例がある。別の画面へ数値だけを移植せず、顔・操作欄・字幕の位置、最長の2行、出現時の動き、スマホ約360px幅での可読性を確認する。

## 8 指摘部分と依存先だけを修正する

変更した素材・主張・台詞と、それを使う動画場面・記事節を結ぶ。音声が変わらなければ再生成せず、事実が変わったときは字幕、見出し、図、記事、概要欄にも影響がないか調べる。旧版を残し、新しい世代へ書き出す。

| 起きた問題 | 次からの対処 |
| --- | --- |
| 冒頭で題材が分からない | 完成像か短い作業見出しを先に示す |
| 人物からGUIへの切り替えが唐突 | 実際の起動画面などで製品と作業場所の前提を短く説明する |
| 文字だけの場面が続く | 人物の疑問、実画面、具体例、関係図へ役割を割り当てる |
| 人物が小さい、表情が乏しい | 主役の場面では大きく使い、会話では話者と聞き手の反応を設計する |
| 手や顔が崩れる、後半の動きが止まる | 参照画と動作の時間配分を見直し、短いカット単位で比較する |
| 金額の先頭がカーソルに隠れる | 読める実録フレームへ替えるか、余白へ移して再撮影する |
| 読みや改行が不自然 | 表示文・読み原稿・意味ごとの改行を分けて直す |
| 声を変えていないのに再生成費用が増える | 検証済み音声の署名を照合し、変更分だけ生成する |
| 共有リンクが開けない | 対象版、権限、処理状況、期限を確認し、必要なら新しいリンクを発行する |
| 技術合格を完成と説明してしまう | 試聴、採用、実機再生、公開を個別の状態で残す |

## 9 動画と記事を同時に作る

動画の調査・撮影・改訂と並行して記事草稿を作り、公式HPの引用候補と記事用のアプリ画面を集める。別の記事依頼を待たない。同じ企画、事実、人物、出典、原素材を共有し、表示用の派生と採用状態を分ける。

動画は用途と結果を伝え、記事は前提、手順、入力例、初回と修正後の比較、数字の照合、注意点を読める形にする。文字起こしだけで済ませず、動画から詳しい記事へ進む理由を作る。複数の短編を一つの詳細記事へつなぐこともできる。

投稿先は `benriworks/blog` が基本で、案件によってnoteも使う。blogのAGENTS.mdと画像規定を確認し、noteにはblog固有のMDX記法を持ち込まない。媒体を指定されたことを公開許可と同一視せず、二重投稿を既定にしない。

共通企画台帳にはCLI・API・Studioの5工程確認画面があり、公開画像の照合と記事向け受け渡しも実装されている。助手がチャットから利用し、ユーザーに操作を求めない。記事本文の自動同期、Drive自動送信、自動公開まで完了したという意味ではない。

## 10 保存場所とGitHubの役割を分ける

| 保存先 | 保管するもの |
| --- | --- |
| `docs/video-production/` | 共通ノウハウ、担当別手順、ひな形、調査記録 |
| `productions/<案件ID>/` | 台本、出典、プロンプト、改訂理由、検証要約、採否 |
| `productions/characters/` | 人物設定、参照版、素材への参照 |
| `outputs/characters/` | 人物原画像、派生、生成動画、比較画像 |
| `outputs/productions/` または `outputs/content-projects/` | 初回出力、修正版、実演原本、音声、レビュー、納品物 |
| 案件内の非公開領域 | 個人情報入りの撮影原本、API生応答、共有受領、秘密を含む記録 |

素材にはID、版、パス、用途、bytes、SHA-256、親素材、作成条件、確認状態を付ける。案件の再開記録から最新版・旧版・原本の台帳をたどれるようにし、既存READMEやレビュー画面も結ぶ。初回と改訂を上書きせず、旧案件の状態ファイルを消して新案件へ流用しない。

worktreeや別PCへ移ったら、コードのルート、素材のルート、実行環境を最初に確認する。cloneだけではignoredの動画・音声・原本や認証情報はそろわない。既存素材を一括移動せず、利用先とバックアップを確認する。

GitHubへは文書、台本、プロンプト、ペルソナ、出典、改善理由、軽量な検証要約と素材の識別情報を残す。**重い動画本体のGitHub保管は不要。動画・音声・納品ZIPはローカルPCと必要な共有ストレージへ置く。** Git LFSやReleasesへの移動も既定にしない。

書き込み先は実際のremoteで確認する。この環境では `fork` が個人の `benriworks/MiniMax-H3`、`origin` が公式upstream。対象パスを指定し、APIキー、署名付きURL、私的原本、無関係な変更をまとめて追加しない。引き継ぎ等の節目で文書をGitHubへ保存し、未採用の規定案は専用ブランチとPRで確認できるようにする。

共通処理を改修した場合は `ARCHITECTURE.md` とMermaid形式の `ARCHITECTURE_DIAGRAM.md` を独立した資料として更新する。個別動画の編集と、Studioの共通機能追加を記録上も分ける。

## 11 レビューを短くし 確認状態を分ける

レビュー用動画はGoogle Driveを優先する。アップロード後に名前、容量、MIME、保存先、アクセス権を読み戻し、処理中ならプレーヤーの状態を確認する。これはスマホ実機再生の確認とは別である。S3はDriveが使えない場合、または会社へ持ち込む用途で指定された場合の代替にする。

依頼には案件と版、投稿タイトル、変更点と秒数、再生・保存リンク、期限がある場合は日本時間の期限、確認してほしい2〜3点をまとめる。長尺では、質問と返答を途中で切らない短い抜粋も用意する。動画と一緒に記事草稿と素材一覧を案内する。

技術検査は全編decode、実寸・fps・実尺、音量と音切れ、字幕、境界フレーム、数字、出典、素材hashを確認する。AIの画像・音声点検、人による最終試聴、ユーザー採用、スマホ実機、公開を個別に記録する。部分的な「声がよい」「この人物がよい」を全話・完成品・投稿への採用に広げない。

## 12 次の1本で確認すること

1. 視聴者と伝える一文、本数・各回の役割を先に決めたか。
2. 今回の主題を実画面で撮れるか確認し、動画と記事の素材を同時に確保したか。
3. 人物・ペルソナ・声の採用範囲を引き継ぎ、役割と物語を設計したか。
4. 完成像、題材見出し、実演前の前提、図と実画面の役割が明確か。
5. 読み原稿、意味ごとの改行、スマホ幅、数字とカーソル、音声実尺を確認したか。
6. 旧版を保持し、変更分だけ生成・描画・再確認できるか。
7. Driveの対象版と記事草稿を示し、技術検査・試聴・採用・公開を分けたか。
