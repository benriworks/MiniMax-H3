## 1. この資料の使い方と採用の範囲

- 新しい企画では、助手が先に調査し、本数・概要・各回で伝える結論・実演案・記事の役割を提案する。ユーザーの伝えたいことを受けて構成を決める。長い入力フォームやStudio操作を依頼の前提にしない。
- 次節以降の型は制作の基準。動画の尺・題材・人物に応じて調整し、変えた理由を案件へ残す。
- シリーズごとの人物・役割・声の採用と、完成物全体の採用は区別する。dots詳細動画での男性の質問役・女性の実務役を、他シリーズへ性別だけで固定しない。
- 「短いほど伸びる」「人物を出せば視聴維持率が上がる」といった効果は未測定。構成の仮説と公開後の実測を分ける。

## 2. タイトルは製品名と具体的な結果を結ぶ

動画とセットで投稿タイトル・動画内の冒頭見出し・概要欄を用意する。基本形は **`【製品名】対象の作業 → 得られる結果・確認する点`**。主役に合わせて `【ChatGPT】`、`【Codex】`、`【Claude】` 等を選び、途中で対象製品を取り違えない。dots編では `【ChatGPT】` から始め、必要に応じてdotsも本文に入れる。

| 用途 | 書き方 | 制作例・案 |
| --- | --- | --- |
| 具体的な作業 | 入力・操作・成果物の組み合わせを示す | `【ChatGPT】Excelからシステムへ自動転記！dotsの実演と人の確認`（今回の投稿文） |
| 視聴者の疑問 | 身近な疑問を一つ置き、何を確認する動画か補う | `【ChatGPT】PCを閉じても仕事が進む？dotsクラウドPCの3つのメリット`（会話内で公開報告のあった例） |
| 実証や修正 | 下書きだけでなく、修正・照合まで何を見せるか伝える | `【Claude】メモからDocsへ！下書きと修正、数字まで確認`（制作時の題名） |

タイトル作成時は次を確認する。

1. 「何の製品か」「何の作業か」「見て何が分かるか」が読めるか。
2. 一つの主要な約束に絞れているか。機能・回数・利点を詰め込みすぎていないか。
3. 「自動転記」「共同編集」「クラウドPC」など、動画で示す行動や仕組みの語を含むか。
4. 疑問形なら本編で回答し、条件・権限・確認が必要なら重要な前提を消していないか。
5. 未測定の時短率、完全自動、ミスゼロ、永久保存などを言い切っていないか。

必要なら結果型・疑問型・実証型を比較案として提示し、推奨案と理由を短く添える。案と採用題名、動画の版を台帳で分ける。シリーズ番号を付ける場合も、番号だけを主題にせず、その1本で分かる内容を残す。

### 投稿タイトル・冒頭見出し・サムネイル・記事題は役割を分ける

| 要素 | 役割 | 今回の例・方針 |
| --- | --- | --- |
| 投稿タイトル | 製品と作業、動画の約束を伝える | `【ChatGPT】Excelからシステムへ自動転記！dotsの実演と人の確認` |
| 冒頭見出し | 音を出す前でも題材を分かるようにする | `Excelの3件を／案件管理へ` |
| サムネイル | 主見出し・人物の表情・実画面の関係を小さくても分かるようにする | 明るさと読みやすさを確認。未採用の案を定番扱いしない |
| 記事題 | 手順・前提・照合を詳しく読めることを示す | `Excelからシステムへの転記をdotsに任せる：登録前の確認と保存後の照合を実演` |

全要素へ同じ長文を貼らない。言い方を短くしても、入力完了を登録完了と呼ぶなど意味を変えない。字幕・タイトル・サムネイルに「MiniMaxで作成」「図解イメージ」等の制作都合の注釈を自動追加しない。必要な出典や架空デモの表示は別に残す。

## 3. 結論ファースト：完成像を見せてから経緯を説明する

冒頭で「この動画を見れば、何ができるようになるか／何を判断できるか」を示す。実際の完成画面や成果物、今回の題材が分かる短い見出しを使う。「dotsの機能を紹介します」だけを先に読む構成から、結果・用途・根拠が見える構成へ変える。

結論を先に伝えても、条件のない成功を約束しない。「架空3件をこのデモ環境へ登録し、照合できた」と、何を確かめた結果なのかを合わせる。途中の失敗や人が確認する場面を省いて、成功したように編集しない。

| 形式 | 基本の流れ | 尺と適用範囲 |
| --- | --- | --- |
| 短尺 | 完成物・得られる状態 → 操作 → 結果の確認 → 注意点 | dots追加編では冒頭1〜2秒で結果を示し、1本1用途・20〜35秒を2〜3本試す指定。全台詞を2秒で読む意味ではない |
| フル動画 | 完成像・題材 → 人物の目的と疑問 → 製品や作業場所の前提 → 実演 → 照合 → 注意点と次の行動 | 必要な説明と実操作を読める長さにする。採用済みの待ち合わせカット等を使う場合も、題材・完成像を伝えることを遅らせない |

フル動画の約5秒の待ち合わせは、この案件で採用された導入例。全シリーズに5秒の人物登場を義務づけない。v04は待ち合わせに題材の見出しを加えた版であり、「完成物を最初の1〜2秒に見せる型」まで実装したとは扱わない。

### 会話から実演へ移る前に、前提を一つそろえる

製品を初めて知る視聴者が置いていかれそうなら、起動画面・実画面を見せながら「何か」「どこで動くか」「何を頼めるか」を短く説明する。長い製品史や一般論へ広げず、その直後に行う操作へ結ぶ。

dots案件では、会話から入力画面へ突然切り替えず、ユーザーが以前渡した起動画面を使って「クラウドデスクトップを持ったパーソナルアシスタントで、そこでブラウザによるデータ入力などを頼める」という前提を置く追加依頼がある。これは**依頼済み・未制作**の項目。元キャプチャの特定、公式根拠と読み原稿、場面追加、後続の字幕・章時刻の更新、書き出し・確認を終えるまで動画へ反映済みとしない。

## 4. フル動画の2人は、質問と実務を通して進める

| 役割 | 担うこと | 台詞の例 |
| --- | --- | --- |
| 視聴者に近い質問役 | 目的、次の操作、判断する場所を尋ねる。分かったことを短く整理する | 「今日は、どんな作業をやりたいの？」「このボタンで保存は終わり？」 |
| 作業を進める実務役 | 目的を答え、操作を案内し、結果を読み、必要なら止まる | 「Excelの三件を移したいの」「まずここを確認するね」「まだだよ。ここは確認画面」 |

dots詳細動画では男性Charonが質問役、女性Aoedeが実務・解説役。同じ架空の成人2人の外見・衣装・左右位置・役割・口調を継続する。人物とペルソナを先に示してユーザーに確認し、確認済みの参照画像からMiniMaxで動かす。シリーズをまたいで顔や性格を無断変更しない。

掛け合いは次の単位で作る。

1. **目的**：質問役がやりたいことを聞き、実務役が対象と結果を答える。
2. **前提**：作業場所や製品が何かを、実画面・短い図でそろえる。
3. **実行**：実務役が「今から何を見るか」を一言伝え、実操作へ切り替える。
4. **疑問と判断**：質問役が誤解しやすい点を聞き、実務役が根拠の画面を示して答える。
5. **結果と照合**：実務役が結果を確認し、質問役が学びを短く言い直す。
6. **締め**：次に試す小さな行動と、必要な権限・人の判断を示す。

女性が喋りながら進める指定では、説明の主導権を外部ナレーターや男性へ戻さない。原稿を機械的に交互読みせず、質問が要らない実演は実務役の短い連続発話でもよい。「なるほど」だけの相づちを増やして尺を埋めない。

質問にはすぐ答え、画面を読む間は説明の後へ置く。各台詞を人物へ割り当て、口調・発音辞書・実音声尺・場面を結ぶ。会話用TTSには、質問を回答として解釈せず、その台詞だけを読むことを指定する。台詞が長ければ内容・構成を直し、語尾を切って収めない。

人物の会話は実演の案内。本人の本当の登録許可や、実際にしていない操作を人物の発言で代用しない。「確認ボタン」と「保存・登録」の違い、人が許可する点、保存後に何を照合するかを画面と対応させる。

## 5. 人物の全面表示とPIPは説明の目的で使い分ける

| 場面 | 表示 | 確認すること |
| --- | --- | --- |
| 待ち合わせ・困りごと・気づき | 人物を大きく、必要なら全面表示 | 題材見出しと顔・手が重ならない。動作を物語へ結ぶ |
| 実演前・要点・注意点・締め | 要点と左右PIP | dotsの質問役は左、実務役は右。表示理由と区間を記録 |
| 入力・確認・登録クリック・詳細比較 | 実画面・図を優先し、PIPを隠す | 操作欄・日付・金額・ボタン・比較表を人物が隠さない |

確認済み人物はMiniMaxで動かす。採用された既存の人物動画を同じ文脈で再利用する場合、映像改訂ごとに生成し直さない。会話中は内容に合った疑問・心配・集中・納得・安心を選び、過剰な怒りや喜びを自動追加しない。

MiniMaxの人物動画と、表情アトラスによる編集アニメーションは来歴を分ける。現行PIPは音声強度で話者の口を開閉し、聞き手は閉口する簡易方式。音素ごとの厳密なリップシンクや、全発話をMiniMaxで生成した動画とは記載しない。

## 6. 実画面・図・字幕・音声の役割を分ける

- **実画面**：何を入力・確認・保存したかの証拠。金額や日付を原寸で点検し、カーソルが桁を隠す場合は読める実フレームへ替えるか再撮影する。数字を描き直さない。入力完了画面と確認画面を取り違えない。
- **図・イラスト**：仕組み、場所、役割、情報の流れを説明する。具体的な利用例と視聴者が確認する点へ戻す。文字を枠で囲んだだけで説明した扱いにしない。
- **字幕・見出し**：短い結論や固有名詞、正確な値を示す。意味ごとに改行し、「表示」を「表／示」に割らない。実フォント幅・読み取れる文字サイズ・スマホ表示を確認する。
- **ナレーション**：操作の意味、条件、理由、次の見る場所を補う。表示原稿と読み原稿を分け、dots＝ドッツ、表＝ひょうなどを対象語句単位で指定する。
- **BGM**：声を支える明るく軽い曲調を基準に、題材に応じて調整する。話している間は下げる。明るさを単なる音量増加に置き換えない。

映像だけの修正では採用済み音声を再利用する。同じ音声の維持が必要なら、WAVやAACの適切な段階で一致を検査する。新しい説明台詞を追加する依頼では、追加分の生成・費用・時刻更新を記録し、「映像のみ修正」としない。費用はモデル・usage・再生成分・単価確認日・仮の為替と、実請求の別を残す。

## 7. 動画から詳細記事へつなぐ

共通の結論・事実・実演・出典・原素材から、動画の短い説明と記事の詳しい手順を作る。既定の投稿先はbenriworks/blog、note指定時は媒体に合わせた派生を作る。動画制作と同時に記事草稿・公式引用候補・記事用の実画面を確保し、別の依頼を待たない。

記事には前提、入力例、初回出力、修正、保存後の照合、注意点を足す。台詞の文字起こしだけにしない。動画用の小さな縦切り出しだけで記事用画像を取得済みとせず、全体と詳細、元寸法、加工、出典を残す。本文の想定表示幅とスマホで確認し、原本不足を拡大処理で隠さない。

動画の締め・概要欄と記事の冒頭で、同じ作業と学びを結ぶ。記事が未公開ならURLを捏造せず、公開後に実URLを追記する。動画の採用から記事の採用・mainマージ・二重投稿・公開を推定しない。

## 9. 初稿・修正版を渡す前の編集確認

- [ ] 投稿題名・冒頭見出し・サムネイル・記事題が、同じ内容を約束している。
- [ ] 冒頭で成果・題材が分かり、初見で必要な製品と作業場所の前提がある。
- [ ] 質問が視聴者の疑問を引き出し、実務役が自然に進めている。
- [ ] 人物の参照・役割・声・左右位置が継続し、顔・字幕・操作欄が干渉していない。
- [ ] 数字と重要語を原寸で確認し、意味を分断する改行やカーソルの重なりを解消した。
- [ ] 必要な図・実画面・公式引用を使い分け、架空例・実証結果・条件を区別した。
- [ ] 声・BGM・読みに問題がないか確認し、再利用と追加生成の範囲を記録した。
- [ ] 記事草稿・素材一覧・出典・不足を動画と同時に案内できる。
- [ ] 対象版・変更時刻・見てほしい点を示し、Drive優先の全編・必要な抜粋を用意した。
- [ ] 技術確認・人の試聴・ユーザー採用・公開を別記録にし、旧版と原本を保持した。

## 10. 保存とGitHubへの引き継ぎ

制作窓口はこのチャット。反復する処理はStudioの共通処理へ反映するが、文書の規定と自動実装を混同しない。既存素材を一括移動せず、案件ID・版・素材ID・相対パス・SHA-256・出典・採用記録からたどれるようにする。レビューはDriveを優先し、S3は指定された会社持ち込みやDriveが使えない場合の代替とする。

**制作した動画そのものをGitHubへ保管する必要はない。** 動画・音声・ZIPはローカルPCと必要な共有ストレージへ置く。GitHubには台本、人物設定、タイトル案、プロンプト、出典、改訂理由、検証要約、再利用の手順を残す。キー・署名付きURL・個人情報入り原本・未整理ログは入れない。通常の書き込み先は個人forkで、公式upstreamへの書き込み、mainへのマージ、YouTube・記事公開は別の指示に基づく。
