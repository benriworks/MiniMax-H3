# 解説動画制作ノウハウ・全工程の引き継ぎ

作成日：2026-10-23。現行PCで制作したdots編・Claude編・比較動画の知見と、ユーザーの要望から定めた運用規定をまとめる。ナレーション担当へは別ファイル [NARRATION_HANDOFF_JA.md](NARRATION_HANDOFF_JA.md) を渡す。

編集基準の更新：2026-10-28。[タイトル・結論ファースト・人物の掛け合い](EDITORIAL_PATTERNS_JA.md) に、制作の型、これまでの修正理由、個別採用と未完了の追加依頼をまとめた。新しい企画・台本・レビュー時に併用する。

## 1. 制作の目的と基本方針

視聴者が「何ができるか」「自分ならどこで使うか」「どこに注意するか」を短時間で理解し、次の行動を選べる動画を作る。単調なテキストの連続を避け、人物の感情・公式画面・実演・図解を、その場面の説明目的に応じて使う。

- ショートは1本1テーマを基本とする。比較や補足は必要なら長くする。
- 新しい機能、提供日、対象地域・プラン、制約は制作時点の公式資料で確認する。確認日と根拠を残す。
- 公式説明の引用、実際に行った操作、架空の利用例、未検証の見通しを区別する。
- 人物や店舗・企画の実演には架空素材を使う。実在の顧客情報を例示素材へ流用しない。
- 「MiniMaxで作成」「図解イメージ」といった制作側の注釈を動画へ自動で出さない。出典表示や、誤解を避けるための「架空の事例」「こちらの実演」は必要な場所に出す。
- 生成物の出所・モデル・設定・原本は制作記録に残す。

## 2. 全工程と確認のタイミング

2026-10-25のユーザー指定により、以下の動画工程には記事草稿とブログ用素材収集を併走させる。調査時に記事構成と出典を整理し、撮影時に公式HPの引用箇所と記事用解像度のアプリ画面を保存し、動画の改訂を草稿にも反映する。動画レビュー時には記事草稿・素材一覧・不足を併記する。動画完成後に別の記事依頼を待って素材を探し直す工程にしない。具体的な保存・確認基準は [共通工程](VIDEO_TO_BLOG_WORKFLOW_JA.md) の「動画制作と記事準備を同時に進める」に従う。撮影不能や記事未完を完了に置き換えず、動画と記事のレビュー・公開状態は分ける。

| 工程 | 担当者が行うこと | 保存物・次に進む条件 |
| --- | --- | --- |
| 0. 企画 | 視聴者、目的、シリーズ、尺、公式根拠、予算・生成回数の目安を定める | 企画書。未決事項を明示 |
| 1. 人物の設計 | **最初に人物キャラとペルソナを作る**。顔・全身・衣装・役割を提示 | キャラクター設定表と比較画像。**ユーザーの明示的な確認を記録するまで本番人物動画・量産へ進まない** |
| 2. 台本と物語 | 人物の課題、試行、気づき、行動に機能説明を絡める | カット割り、表示文、読み上げ原稿、出典、場面の目的 |
| 3. 素材 | 確認済み人物をMiniMaxで動かす。公式引用と実演を撮る | 人物動画、初回出力・修正画面、素材の来歴 |
| 4. 音声 | 読み方と速度を決め、短い試聴を経て場面別に生成 | WAV、表示原稿と読み原稿、生成記録。別冊の音声手順に従う |
| 5. 1本の初稿 | 人物・引用・実演・字幕・音声・BGMを組み合わせる | 完成MP4、360px幅の確認画像、全場面一覧、見出し案 |
| 6. 初稿レビュー | 1本を見てもらい、人物・テンポ・理解しやすさを確認する | 指摘と対象版。シリーズ量産の基準を先に固める |
| 7. シリーズ制作 | 確定した人物と演出を引き継ぎつつ、課題・動作・実演を変える | 各話の独立世代。原稿や声の無断変更を避ける |
| 8. 確認と修正 | 媒体・画面・音・出典を検査し、指摘部分を直す | 修正前後、変更理由、再確認結果。旧版を保全 |
| 9. 納品 | MP4、投稿見出し、説明欄、字幕、出典をそろえる | ローカル納品ページ、共有リンク、期限、レビュー状態 |
| 10. 資産化 | 採用ルール・失敗と改善・再利用素材の索引を更新する | 文書をGitHubへ保存。動画本体はローカル／共有ストレージ |

人物の初期確認は必須。初稿レビューは大量生成による手戻りを避ける基準工程とする。既にユーザーが確認した判断は、対象の版・範囲を引き継ぎ、同じ確認を繰り返さない。通常の修正・検査を細切れの承認待ちにしない。

## 3. 人物キャラを先に決める

[CHARACTER_BIBLE_JA.md](templates/CHARACTER_BIBLE_JA.md) に、キャラID、成人・架空であること、外見、衣装、体格、配色、性格、仕事、得意不得意、視聴者との関係を記す。人物は知的で親しみやすく、過度に狙った外見やポーズにしない。体格の調整は自然な範囲で行う。

確認依頼では、同じ人物の顔・全身・動画に入る構図を示す。候補は比較しやすい数に絞り、「顔と雰囲気」「衣装」「役割」の3点程度に確認対象を限定する。採用画像のID・版・hash、ユーザーの返答、日付、採用範囲を残す。返事がないこと、AIの画面検査合格、担当者の好みをユーザー承認の代わりにしない。

既存シリーズでは、ユーザーが指定した元の二人を基準にする。新しい人物を別シリーズへ使う場合も、シリーズの人物台帳へ割り当てを記録する。キャラの顔だけでなく、衣装・配色・背景・役割・口調を引き継ぐ。

現行資料にはdotsの元の男女、Claudeの企画担当「佐伯栞」、Codexの業務改善担当「高瀬誠」、比較用人物の候補がある。これらの候補や完成素材に `user_approved: false` がある場合は、その状態を維持する。既存素材があることだけで、新シリーズへの採用が決まったとは扱わない。

## 4. 人物に物語を持たせる

人物を単なる飾りとして置かず、その人の仕事に小さな課題を作る。基本の流れは「困りごと → 試す → 画面で確かめる → 気づく → 次の行動」。人物がAIを使って何を変えたかを見せる。

例：企画担当がメモを企画書へまとめる → 同じ企画を会議資料にする → 告知を整える → 一文を修正する → ファイルを持ち出して確認する。同じ架空企画の価格・日付・予算を各回で維持すると、視聴者が前回からの続きとして追いやすい。

- 各話の冒頭に完成像・短い結論や「今回の課題」、最後に「今回得たこと／次の仕事」を置く。結果を見せてから経緯を説明し、長い製品紹介や挨拶だけで始めない。
- 二人を使う場合は、質問・試行役と整理・検証役など、役割を明確にする。能力や性格を性別だけで決めない。
- キャラ自身の発話か外部ナレーションかを台詞ごとに決める。従来の短尺にはAoedeの単独解説があり、dots詳細動画v03以降は男性Charonの質問・女性Aoedeの回答と実演進行を使う。声の数や役割を全動画で同一とせず、PIPの簡易口パクを厳密なリップシンクと扱わない。
- 新しい話で前回の事実を矛盾させない。変更した設定は人物台帳とシリーズ年表へ記録する。

## 5. 確認済み人物をMiniMaxで動かす

同じキャラの確認済み画像をMiniMaxの参照・始点に使う。毎回テキストだけから顔を生成し直さない。I2VAは始点から動きを作る用途、FL2VAは始点と終点を指定したい用途に使い分ける。方式が同じでも外見や動きが完全固定される保証はないため、生成後に照合する。

1. キャラID・版と参照画像を固定する。
2. 動画に必要な表情・動作を先に決める。例：考える、気づく、小さくうなずく、資料を示す、落ち着いて締める。
3. 1カットの主役と主動作を絞る。顔・髪・服・背景を維持し、カメラは必要以上に動かさない。
4. 正確な文字・製品名・ロゴは生成に任せず、編集で加える。
5. まず短い1本を作り、顔・体格・手指・衣服・動作を確認してからバリエーションを増やす。
6. 冒頭・中盤・末尾の実フレームを見て、静止画の拡大だけになっていないか、意図した動きがあるかを確認する。

現在の人物素材は768×1376、24fps、124フレーム、約5.167秒の例がある。生成指定の「5秒」と編集上の正確な尺を混同せず、毎回実ファイルで測る。素材より長い場面では、ナレーションを切らず、素材終了前からまとめ画面へ移る。無断のフリーズ延長・ループで長さを埋めない。

人物を画面全面に効果的に出し、表情と身ぶりを主役にする。顔の上へ文字を置かない。公式引用・実演の重要部分には人物を重ねず、場面を切り替える。毎回同じ動作の同じ部分だけを使い続けず、承認済みの人物像のまま動きと構図の変化を用意する。

## 6. 公式資料と実演を見せる

具体的な撮影操作・表示倍率・原本の扱い・製品画像の引用・人物との切り替えは [PC画面撮影と公式引用の別冊](SCREEN_CAPTURE_AND_QUOTES_JA.md) を使う。静止画はWindowsキー＋Shift＋S等で実画面を撮り、PNGを保存して開き直す。録画は対象領域・時間・音声の有無を決め、操作前後の余白と結果を読める時間を残す。

- 公式サイトは制作時に確認し、URL・ページ名・確認日・引用箇所・対象プランや地域の条件を残す。最新性を推測しない。
- 引用画面へ出典を表示する。説明欄に詳細な出典と確認日を置く。画像利用条件を確認する。
- 公式の製品画像・UI画像も利用できる素材の候補とするが、掲載ページと取得元、利用条件を記録する。公式画面の引用と、配布用製品画像の素材利用を区別し、出典表示だけですべての利用が可能とは扱わない。
- 必要な箇所だけを読める大きさで撮る。実画面を拡大して撮り直せるなら、低解像度画像の後処理拡大より優先する。
- UIや文字を生成AIで描き直したものを公式画面・実証画面として使わない。
- 実演は入力、初回出力、修正依頼、修正後を保存する。修正により意味や数値が変わっていないか確認する。
- Word／PowerPointへの書き出しは、メニューの存在、ファイル取得、内容検査、別アプリで開く確認を分ける。
- 会話名・アカウント・メール等が入った原本はローカルの `_private/` に保持し、公開用切り出しとは分離する。

## 7. 演出と画面の知見

### タイトルとフル動画の基本形（2026-10-28整理）

投稿題名は主役に合った `【ChatGPT】`・`【Codex】`・`【Claude】` 等と具体的な作業・結果を結び、動画とセットで渡す。投稿タイトル、動画内の短い見出し、サムネイル、詳しい記事題は役割を分ける。未検証の効果を煽らず、疑問形の題名には本編で答える。

フル動画は、完成像・題材→人物の目的と疑問→必要な製品・作業場所の前提→実演→照合→注意点と次の行動を基本形とする。2人は説明文を交互読みするのではなく、質問役が目的や判断を尋ね、実務役が答えながら進める。初見で分からない製品や作業場所には、実画面による短い説明を挟む。具体例と適用範囲は [編集の型](EDITORIAL_PATTERNS_JA.md) を参照。

### 完成物から始める短尺の試作（2026-10-25）

dotsクラウドデスクトップの追加編では、冒頭1〜2秒で成果物・得られる状態を実画面で示す。長い挨拶や「機能を紹介します」という前置きを省き、結果の先出し→操作→結果の確認→用途に即した注意点を、1本1用途・20〜35秒で試す。冒頭の文章全体を2秒で早口に読み切る指定ではない。人物の登場は成果物の表示を遅らせず、その後の気づきや行動に結び付ける。

最初は2〜3本の小規模な試作とし、1本目の初稿を確認してから残りへ適用する。短ければ必ず伸びると断定せず、完成物の先出しと用途の具体化を検証仮説として記録する。用途・尺が異なる動画の結果を厳密なA/Bテストの効果と呼ばない。公開後の数値は取得した指標名・分母・経過時間とともに記録し、自動監視や予約投稿を勝手に設定しない。

同日の追加指示により、クラウドデスクトップ編は一時的な環境でもできた単純な画像・表の生成だけを主題にせず、実アプリのGUI、操作交代、修正、保存した作業の再表示を見せる。題材はBlenderでのどら焼き制作、Excelファイルから疑似クラウドシステムへの入力へ変更する。仮想デスクトップでしか不可能と断定せず、撮影した具体的な工程を根拠にする。疑似システムにはデモ環境と表示し、実サービスへの登録実績と混同させない。

### 図で仕組みと自分との関係をつなぐ（2026-10-25追加）

ユーザーは、説明したい要素を図・イラストで示し、周辺の利用例と自分との関係が分かる説明を指定した。具体例と抽象的な仕組みの説明を必要に応じて行き来する。文字を図形で囲むだけでは図解した扱いにしない。

- 台本では、各要点に「視聴者に理解してほしいこと」「具体的な利用例」「仕組み・位置関係・因果」「視聴者が確認・行動すること」を対応付ける。尺に応じて複数カットへ分け、1画面へ詰め込まない。
- 具体例は、対象視聴者が使う場面から選ぶ。例から登場者・処理する場所・情報の流れを抽出し、図で仕組みを示した後、具体的な確認先や行動へ戻す。説明しやすければ仕組みから具体例へ進む順でもよい。
- 図には、利用者・対象システム・その中で動く機能などの境界と役割を示す。矢印はアクセス、応答、依存、処理の順序など何を意味するか分かるようにし、発話に合わせて強調する。
- 周辺事例を、全サービスに共通する事実や今回の影響範囲として扱わない。例示・統計・一般的な仕組み・確認済みの事実・条件付きのリスクを区別する。抽象化や比喩で重要な条件を消さない。
- 人物は視聴者の疑問・気づき・行動を担う。仕組みは図解、実際の操作や証拠は実画面・公式引用で示し、説明目的に応じて切り替える。正確な名称・数値・短い結論には文字を使う。
- レビューでは「何が起きるか」「どの身近な場面とつながるか」「自分なら何を確認するか」を画面とナレーションから追えるか確認する。抽象的な見出しの読み上げだけになっていれば、例や関係図を補う。

PHP案件では、既存のWordPress・フォーム・買い物の例と、利用者→サーバー内での処理→画面への応答の図をこの説明方針の出発点とする。さらに具体化する場合は、同じ架空サイトでの操作と返る結果を対応させる。最新版の動画を再制作したかどうかは案件記録へ別に記載する。

従来のショート標準出力には1080×1920、24fps、30秒で720フレームの実績がある。追加編には30秒・35秒、比較動画には75秒、横長詳細動画には約4分の実績がある。尺を一律に30秒へ固定せず、題材・実音声・実演と今回の指定に合わせる。これらは当プロジェクトの制作例であり、配信サービス全体の上限を示すものではない。

- 冒頭の数秒で課題と見たい結果を示す。長い前置きや制作ツールのクレジットを入れない。
- 見出しは結論、ナレーションは理由・条件・補足にする。全文章を同時に表示しない。
- 人物動画、実演、公式画面、動く図解を目的に応じて切り替える。カット数を増やすだけでなく、各場面に新しい情報を持たせる。
- 現行の文字の目安は主要文字54px以上、CreatorShort字幕66px。2行字幕の上下余白・枠・出現時の動きまで含めて検査する。
- 現行実装の字幕安全域は下端1490px、CreatorShort字幕は従来位置から33px上へ調整済み。比較compositionは独立配置。数値だけを別のテンプレートへ移植して合格としない。
- 360px程度のスマホ幅で確認する。公式キャプチャ内の文字も読みやすさを確認する。
- 字幕の出現時、最長の2行、人物と公式画面の切り替え、素材の終わりを実フレームで確認する。

## 8. ナレーションとBGMの引き継ぎ

基本の声はユーザーが選んだGeminiのAoede、Koreは必要に応じた候補。自然な標準日本語で、少し速めでも理解しやすい読み方にする。小数点付きの製品名は例として「Fable5.1 → フェイブルごーてんいち」、整数の「5」は「ファイブ」でよい。表示原稿と読み上げ用原稿を分ける。

生成・編集・組み込みの実務は [ナレーション別冊](NARRATION_HANDOFF_JA.md) に集約する。音声APIの成功、声の選択、完成動画の試聴は別の確認。完成品を聞いていなければ「最終試聴未実施」と明記する。

BGMは権利と出所を記録し、ナレーション中は音量を下げる。生成した人物動画の音は通常ミュートし、ナレーション・BGM・効果音を編集で統一する。映像だけを直す際は音声を再生成せず、再利用と一致確認を優先する。

## 9. ローカルPCの保存ルール

保存先の役割を固定する。既存の納品物を整理のために一括移動せず、まず台帳から参照する。今後の案件では次の構成を基準にする。

```text
MiniMaxH3/
  docs/video-production/                制作規定・引き継ぎ・ひな形
  productions/<production-id>/          軽量な台本・出典・制作記録・採否
  productions/characters/<character-id>/ 人物設定と素材への参照
  outputs/characters/<character-id>/<version>/
    reference/ motion/ review/          原画像・MiniMax動画・比較画像
  outputs/productions/<production-id>/<generation-id>/
    inputs/                            使用入力と対応表
    _private/                          個人情報入り撮影原本・非公開文脈
    raw/                               初回生成原本
    captures/                          公開可能な引用・実演の切り出し
    narration/                         場面別WAV・原稿・生成記録
    review/                            比較画像・レビュー記録・確認ページ
    release/                           確認対象のMP4・字幕・投稿情報
    manifest.json                      媒体仕様・bytes・hash・来歴
  outputs/sharing/<date-or-project>/    共有の検証記録（署名URLなし）
```

既存ドライバーの `voice-generations/`、`public/`、`preview-*.png` 等は上記の役割に対応する既存形式として利用し、改名・移動で参照を壊さない。

- production IDは `SHORT_YYYYMMDD_topic_30s` など、種類・日付・内容が分かる形式にする。例は将来案件用で、既存IDは変更しない。
- 世代IDはUTC日時と識別子、人物版は `v01` などで区別する。表示する期限・レビュー時刻には日本時間等のタイムゾーンを付ける。
- 素材はID、用途、版、相対パス、bytes、SHA-256、親素材、作成条件、レビュー状態で索引する。`asset-catalog.example.json` は記載例であり、自動実装ではない。
- 画像はPNG等の原本と表示用派生、音声は元WAVと編集用、動画はrawと完成MP4を分ける。
- `final2`、`final-final` を最新版の根拠にせず、`state.json` は作業中、`delivery.json` は検証済み納品候補を指す。GitHubへ公開する台帳は必要な項目だけを別に整理する。
- 1案件の `README` または `review/index.html` から、最新版・前版・人物・音声・出典・指摘・納品物をたどれるようにする。リンクの実在を確認する。
- 再利用のために検証済み素材を残す。削除・圧縮・別ドライブへの移動は、利用先を確認してから行う。GitHubを動画バックアップと見なさず、重要な原本・採用素材・完成品は別媒体にもバックアップし、復元とhashを確認する。

## 10. レビュー依頼と変更の扱い

[REVIEW_REQUEST_JA.md](templates/REVIEW_REQUEST_JA.md) を使い、対象ID・版・変更点・確認してほしい点・リンク・期限を一度に示す。確認項目は2〜3点を基本とする。

| 段階 | 見てもらうもの | 確認すること |
| --- | --- | --- |
| 人物の初期確認 | 顔・全身・動画の構図・人物設定 | 外見、衣装、雰囲気、役割の採否 |
| 初稿 | まず1本のMP4、見出し、全場面一覧 | 分かりやすさ、人物の使い方、テンポ、声 |
| 修正版 | 同じ条件の前後比較、変更した秒数 | 指摘への対応、他の場面や音声への影響 |
| 最終版 | MP4、見出し、説明欄、字幕、出典 | 最終試聴、採用、公開判断 |

PCではローカル確認ページと絶対パスのリンクを渡す。**2026-10-23の追加方針により、レビュー動画はGoogle Driveを優先する。** 同じ案件のフォルダーへ版を付けて保存し、スマホで開けるリンクを渡す。アップロードとメタデータ確認、動画処理完了、実機再生は別に記録する。共有権限を無断で一般公開へ変更しない。当面はこのチャットで制作を進め、ユーザーにStudio操作を求めない。

S3はDriveが使えない場合、または会社へデータを持ち込むためにユーザーが指定した場合に使う。再生リンクとMP4保存リンクには対象版・有効期限（日本時間）を添える。期限切れの際は新リンクを渡し、同じURLの期限が自動で伸びたとは説明しない。現行S3upは再発行から最長24時間で、元の期限へ1日を加えられるとは限らない。

指摘は「00:08〜00:11、文字を大きく」「人物Bはv02を採用」のように対象を特定する。担当者は、指摘内容、変更したもの、変えていない範囲、再検証結果を残す。曖昧な「OK」を全素材・全話・公開の承認へ拡大しない。

状態は少なくとも、技術検証、AI補助による画面確認、人による最終試聴、ユーザー採用、公開可否、実投稿を分ける。未実施は `pending`、採用未確認は `false` とする。技術合格をユーザー承認と混同しない。

## 11. GitHubへ継続して資産化する

**動画自体は重いため、GitHubへの保管は不要とする。** raw・完成MP4・レビュー動画を、Git LFSやGitHub Releasesへ既定で送らない。大きい音声・画像原本・納品ZIPもローカル／共有ストレージで管理する。

GitHubへ残すのは、制作ルール、人物設定、台本・表示文・読み原稿、プロンプト、出典と確認日、再利用手順、修正理由、失敗と改善、検証要約、素材の識別情報。小さい参照画像を置く場合は、権利・個人情報・必要性を確認し、対象を指定して追加する。

更新の節目は「人物・演出方針の確定」「初稿レビュー反映」「生成・読み・字幕の改善」「シリーズ納品」「引き継ぎ」。各節目でローカル文書を更新し、内容を見直してGitHubへコミット・プッシュし、必要ならPRでレビューする。オフライン等で送信できなければ、未送信と対象を記録して次の同期時に反映する。自動同期ツールを実装済みとは扱わない。

現在の保存先は個人forkの `benriworks/MiniMax-H3`。書き込み前にremoteとbranchを実際に確認する。この環境の `origin` は公式upstreamなので、名前だけで保存先を選ばない。無関係なローカル変更、動画、秘密情報を一括コミットしない。

APIキー、署名付きURL、個人情報入り撮影原本、未整理ログを文書やGitHubへ保存しない。共有記録にはファイル名・サイズ・hash・共有ID・期限・検証結果を残し、署名URLは受け渡し時だけ扱う。動画の所在は期限付きURLではなくローカル相対パスとhashで追う。

アプリを改修した場合は、独立した `ARCHITECTURE.md` と `ARCHITECTURE_DIAGRAM.md` を更新する。制作手順の変更はこのガイドへ、技術実装の変更はアーキテクチャへ記録し、両者を混同しない。

## 会話とPIPの演出規則（2026-10-26追加）

ユーザーは、採用した待ち合わせから同じ2人の会話で自然に本編へ入り、本編では男性を左・女性を右のPIPとして、場面の規則に沿って出すよう指定した。従来の全面表示は導入・人物を主役にする場面で用い、本編の指定された場面にはPIPも選べる。全面表示だけを全人物場面に必須としない。

PIPを出すのは実演前、要点の強調、注意点、締め。入力欄・確認画面・登録クリック・詳細な値の照合を読む間は非表示とし、中央の情報、左右の顔、下部の字幕を分離する。左右位置はシリーズで固定し、区間と理由を台帳に残す。話者の口だけを動かし、聞き手は閉口して疑問・困り・集中・安心などの反応を示す。内容に合わない怒りや大げさな喜びを自動で付けない。

MiniMaxの人物原本と、静止画アトラスの編集アニメーションを分けて記録する。音声強度による開閉は簡易口パクと呼び、音素単位の同期を確認済みとしない。原音声の発話区間、表情の選択、開閉口、聞き手の閉口、字幕と画面の可読性を確認する。ユーザーの人物カット採用を、新しい台詞や完成動画の採用・公開へ拡張しない。

具体例と検証は `productions/LONG_20261026_dots_transfer_detail/PIP_POLICY_V02_JA.md`。規則は共通CLIに保存し、Studioの操作をユーザーへ求めない。
