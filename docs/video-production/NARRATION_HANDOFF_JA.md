## 1. 最初に担当者へ渡すもの

2026-10-28更新：単独解説と2人の掛け合いを区別する。題名・結論ファースト・人物の役割と全体構成は [編集基準](EDITORIAL_PATTERNS_JA.md)、会話TTSと実尺配置は [会話の別冊](DIALOGUE_NARRATION_JA.md) を併用する。

| 渡すもの | 必要な内容 |
| --- | --- |
| 案件情報 | production ID、動画の目的、対象視聴者、尺、シリーズ、対象版 |
| 表示用原稿 | 製品名・数字・日付を正しく書いた原稿。字幕と説明欄の基準 |
| 読み上げ用原稿 | 場面別の読み原稿と、固有名詞・小数点・略語の読み方 |
| カット割り | 場面順、予定尺、人物の動作・引用・実演のどこで何を話すか |
| 声の基準 | 採用済みの短い試聴音声、voice名、読み方・速度の指示 |
| 修正情報 | 初回か差し替えか、変更する場面、再利用する音声のIDとhash |
| 確認方法 | レビュー担当、確認対象の時刻、受け渡し先、返答期限があればその日時 |

原稿、声、速度、発音辞書を先にそろえる。モデルのAPIキーを原稿・台本・引き継ぎファイルへ書かない。声の採用と完成動画の最終試聴は別の確認として記録する。

## 2. この制作で採用した声と読み方

- 基本：**Aoede**。ユーザーが試聴して選択した声。
- 候補：**Kore**。必要な回で比較する候補。担当者だけの判断でシリーズの声を毎回変えない。
- dots詳細動画の2話者：女性の実務・解説役は **Aoede**、男性の質問役は **Charon**。v03動画の採用記録を参照し、他シリーズへの割り当ては個別に決める。
- 2026-10-26の制作で使用したモデル：`gemini-2.5-flash-preview-tts`。再実行時の利用可否・料金は改めて確認する。
- 読み方：自然な標準日本語。明瞭で親しみやすい、落ち着いた解説。**少し速めでも理解できる速さ**。
- 原稿以外の前置き、あいさつ、BGM、効果音、余計な語句を音声生成へ追加させない。

生成時の指示の基準：

```text
Read only the supplied transcript, in natural standard Japanese.
Use a clear, friendly professional explainer voice, slightly brisk but easy to follow.
No music, introductions, sound effects or extra words.
Transcript:
（ここに読み上げ用原稿）
```

現行Gemini経路の速度はこの指示と原稿・区切りで調整する。`story.rate` を1.1へ変えるだけでGeminiが1.1倍になる実装ではない。一定倍率を指定できると説明しない。速すぎる場合は一文を短くし、固有名詞の前後に自然な区切りを置き、短い試聴から決める。

## 3. 固有名詞・数字・小数点の発音

表示原稿と読み上げ原稿を分離する。ユーザーの指定例は次のとおり。

| 表示 | 読み上げ |
| --- | --- |
| Fable5.1 | フェイブルごーてんいち |
| Fable5 | フェイブルファイブ |
| Claude | クロード |
| dots | ドッツ |
| 元の表／この表 | 元のひょう／このひょう |
| Excel | エクセル |

小数点付きの「5.1」を「ファイブポイントワン」に戻さない。整数の「5」は「ファイブ」でよい。別の製品名・略語の読みが不明なら、生成前に公式の読みやユーザー指定を確認する。

台本の発音辞書の例：

```json
{
  "pronunciations": [
    {"source": "Fable5.1", "target": "フェイブルごーてんいち"},
    {"source": "Fable5", "target": "フェイブルファイブ"},
    {"source": "Claude", "target": "クロード"}
  ]
}
```

長い語から置換し、「Fable5」を先に置換して「Fable5.1」を壊さない。数字の「5」だけを全文一括置換しない。日付、金額、プラン名、読み上げ不要のURLにも注意する。表示原稿は読み仮名で上書きしない。

「表」を一律に「ひょう」へ置換して「表示」等を壊さない。対象語句と文脈を指定し、表示名はdotsのまま、読み原稿だけをドッツにする。

## 4. 生成前の準備

現行PCはWindows、PowerShell 7、Python仮想環境、FFmpeg／ffprobeを使う。APIモデルの利用可否・料金・利用枠は、実行する担当者の環境で事前に確認する。新しい担当者にはリポジトリの版と必要な制作コードを渡す。**このMarkdownだけでモデル、認証、生成コード、素材が導入されるわけではない。**

Geminiキーは実行プロセスの `GEMINI_API_KEY` で読む。現行コードには `GOOGLE_API_KEY` の代替もあるが、前者が設定されていると優先される。値は画面共有・チャット・GitHub・コマンド引数へ出さない。担当者のアカウントで設定し、他人のキーを資料に添付しない。

Windowsでユーザー環境変数だけに設定した場合は、アプリを起動し直す。古いプロセスに以前のキーが残ることがある。次は**設定の有無だけ**を見る例で、APIは送信しない。

```powershell
[bool]$env:GEMINI_API_KEY
```

ユーザー環境変数の新しい値を現在のPowerShellへ読み直す必要がある場合の例：

```powershell
$env:GEMINI_API_KEY = [Environment]::GetEnvironmentVariable('GEMINI_API_KEY', 'User')
[bool]$env:GEMINI_API_KEY
```

キー自体を表示する確認はしない。設定確認のたびに有料生成を試さず、原稿・声・対象版・実行回数を決めてから送る。

## 5. どう生成しているか

現行アダプターはGeminiの `generateContent` へ原稿を送信し、`responseModalities: ["AUDIO"]` と `prebuiltVoiceConfig.voiceName: "Aoede"` を指定する。送信先は `https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash-preview-tts:generateContent`。これは実装の説明であり、以下のJSONを貼るだけで送信されるものではない。

これは従来の単独ナレーター経路の例。2話者の共通 `tools/studio/dialogue_narration.py` は話者に応じてAoede／Charonを指定し、1台詞ずつ生成する。`conversational_v3` は引用台詞だけを自然な成人同僚の会話として読み、質問を回答として解釈しないと指定する。解説文を機械的に交互読みせず、質問と実務の進行へ原稿を組み直す。

```json
{
  "contents": [{"parts": [{"text": "（読み方の指示と読み上げ用原稿）"}]}],
  "generationConfig": {
    "responseModalities": ["AUDIO"],
    "speechConfig": {
      "voiceConfig": {"prebuiltVoiceConfig": {"voiceName": "Aoede"}}
    }
  }
}
```

現行実装は1場面ずつ生成し、応答を24kHz・モノラル・16bit PCMのWAVとして保存する。元のPCMサンプル数から実尺を測り、全体音声・時刻表・生成記録を作る。30秒7場面の回なら通常7要求、5回で35要求が当初計画となる。単なる例であり、失敗・結果不明を0件に数え直さない。

本番の生成要求の間隔は現行シリーズドライバーで22秒以上。これは本プロジェクトの運用設定で、Gemini全利用者に共通の保証値ではない。モデル・利用枠変更時は見直す。

## 6. 現行コードを持つ担当者の実行手順

現在のコードの参照先：

- TTSの送信・WAV検査：`productions/SHORT_20261021_dots_cloud_benefits/gemini_voice_trial.py`
- 場面別音声の生成・再開・配置情報：`productions/SERIES_20261022_dots_finale/produce.py`
- Claude編の専用ドライバー：`productions/SERIES_20261022_claude_work/produce.py`
- 音声の読み込み・場面配置・合成：`tools/studio/shorts_creator.py`
- 2話者の台詞生成・送信記録・PCM検査：`tools/studio/dialogue_narration.py`
- フル動画の実音声尺・回答後の間・明るいBGMと減音：`tools/studio/longform_audio.py`
- dots詳細動画の採用済み会話台本：`productions/LONG_20261026_dots_transfer_detail/narration-v03-ja.md`

これらは現行PCのコード位置であり、GitHubへ文書を保存しただけで制作コード一式も共有済みとは限らない。別PCでは必要な版のコードと環境の引き継ぎを確認する。新案件は独立したproduction IDと原稿を用意し、既存回のファイルや `state.json` を消して使い回さない。

以下は**既存Claude編の処理を説明する参照コマンド**。新案件をそのまま生成する汎用コマンドではない。リポジトリのルートを開いたPowerShellで使う。

```powershell
# 1. 入力を確認。外部の音声APIは呼ばない
.\.venv\Scripts\python.exe productions/SERIES_20261022_claude_work/produce.py preflight --episode 1

# 2. 場面別音声を生成。未生成分は有料APIを利用する
# 対象原稿と回数を確認し、生成の指示がある場合に実行する
.\.venv\Scripts\python.exe productions/SERIES_20261022_claude_work/produce.py generate --episode 1

# 3. 検証済み音声を読み込み、映像の配置を準備する
.\.venv\Scripts\python.exe productions/SERIES_20261022_claude_work/produce.py prepare --episode 1

# 4. 動画を描画・合成する
.\.venv\Scripts\python.exe productions/SERIES_20261022_claude_work/produce.py render --episode 1
```

最初に1本を確認し、いきなり `--episode all` で量産しない。既存の検証済み音声がある場合はhashと原稿を照合して再利用する。Koreの試聴はアダプターが対応するが、ここで参照した従来のClaude／dots短尺シリーズドライバーはAoede固定である。2話者の詳細動画は別の `dialogue_narration.py` を使う。voice名だけを変えればどの経路でも同じまま動くと説明しない。

既に検証済みの場面別音声を共通編集処理へ渡す入口は次のとおり。これは**音声生成をしない**。

```powershell
.\.venv\Scripts\python.exe -m tools.studio.shorts_creator prepare --story productions/<新案件ID>/creator-story.json --narration-source outputs/productions/<新案件ID>/<音声世代>/voice-source.json
```

山括弧は実際のパスへ置き換える。`voice-source.json` を手書きで作って未検証WAVを通さず、生成記録・原稿・hashの一致する素材を使う。

## 7. 失敗と再生成の判断

| 状態 | 対応 |
| --- | --- |
| 生成済み・検証済み | WAV・原稿・hashを照合して再利用。映像修正のためだけに再送しない |
| APIキー無効等の明確な拒否 | 記録を残し、設定と対象を確認してから、置換する1件を明示して再実行 |
| timeout等で結果不明 | 自動再送を止める。元の送信記録を保存し、事業者側の結果や課金を確認 |
| 発音や声が不適切 | 指摘箇所を特定し、新しい原稿・版で対象場面を生成。旧WAVを残す |
| 音声が場面に収まらない | 文を短くするか構成・尺を見直す。文末を切って合わせない |

中途半端な出力フォルダーや送信記録を削除して「初回送信」に戻さない。成功、拒否、結果不明、再生成を別々に数える。APIが成功しても実請求額が照合済みとは限らない。usage・モデル・確認日を残し、料金は事業者の最新単価と実際の請求で確認する。

費用を伝えるときは、最新版の追加生成分、旧版・やり直しを含む累計、音声点検、その他の映像制作費を分ける。為替は仮定か実測かを示し、生成ログからの概算を請求確定額としない。映像だけの修正で新しいTTS送信がなければ、その修正の追加音声生成分は0回と記録できる。

## 8. 動画への入れ方：共通処理を使う場合

1. `voice-source.json` と元WAV・原稿・生成記録を照合する。
2. WAVの実サンプル数で各場面の音声時間を測り、24fpsのタイムラインに配置する。現行CreatorShortは各場面の冒頭に3フレームの余白を置く。
3. 字幕は実発話区間の中へ配置する。現行は文字量による区間配分であり、単語単位の強制アライメントではない。聞いてずれを確認する。
4. MiniMax人物動画の元音をミュートし、案件で採用した声を各台詞へ置く。単独解説ではAoede、dots詳細動画の掛け合いでは質問役Charon・実務役Aoedeを使う。
5. BGMと効果音は別トラックにし、話している間はBGMを下げる。ナレーションの聞き取りを優先する。
6. 48kHz・ステレオAACへ最終合成する。音声の元24kHzを48kHzへ変換しても、生成音質自体が向上するとは説明しない。
7. 現行の完成音量の検査範囲は-18〜-14 LUFS、true peakは-1dBTP以下。これは本制作の基準で、YouTube全体の必須規格ではない。
8. 完成MP4の全decode・音量・字幕を確認し、**BGM込みの完成品を最終試聴**する。

フル動画では質問と回答を短い間でつなぎ、画面を読む時間は回答・操作説明の後へ置く。現行の `pause_mode='after_answer'` は今回の男性質問／女性回答の役割に合わせた指定で、別の配役へ無条件で適用しない。明るい伴奏の `music_style='bright'` も案件で選び、声の下で減音する。詳細は会話の別冊を参照。

映像だけを修正する場合は採用音声の再利用を優先し、v04ではv03のAACをコピーして抽出音声のSHA-256一致を確認した。新しい導入説明を追加する場合は追加台詞だけを別版で生成し、後続の時刻表・字幕・BGM・動画尺を更新する。音声が増えた改訂を「音声は完全に同一」と記録しない。

2026-10-31のProニュースv04はBGMだけの改訂例。声原本6件・配置・ピーク基準を保ち、`tools/studio/music_mix.py` で通常部と頭尾、発話中の減音を調整した。`music_bright()` は既定の曲とフェードを保ちながら任意フェードを指定できる。BGMを変えた後のAAC全体は旧版と一致しないため、声成分のPCM一致、映像のbitstream一致、最終ミックスのラウドネスとtrue peakを別々に確認する。設定と実測は[案件の音量改訂](../../productions/content-projects/CONTENT_20261030_chatgpt_pro_usage_news/AUDIO_REVISION_V04_JA.md)。

## 9. 別の編集ソフトで組み込む場合

編集担当へ、場面別WAV、表示原稿、読み原稿、場面ごとの時刻表、必要なら連結済みWAVと音量基準を渡す。連結WAVは無音を除いて並べただけの場合があるため、動画の0秒へ置くだけで既存版と同じタイミングになるとは限らない。カット割りと時刻表を基準に合わせる。

人物動画の音を消し、声・BGM・効果音を別トラックにする。声の前後を短く切り詰めすぎず、語尾を残す。映像素材が短ければ、まとめ画面や別カットへ移り、音声は最後まで流す。速度変更を行う場合は変更率と方式を残し、音程・聞き取り・字幕時刻を再確認する。

納品形式や編集ソフトを変えた場合も、元WAVは上書きしない。書き出した完成MP4を聞き、声の途切れ、二重再生、BGMに埋もれる箇所、左右の偏り、字幕とのずれを確認する。

## 10. 試聴と修正の依頼方法

まず声だけの短い試聴、次にBGM・映像を含む完成動画で確認する。全原稿を音声化する前に「声」「速さ」「固有名詞の読み」をそろえる。

依頼文の例：

```text
対象：＜案件ID／版＞、Aoedeナレーション
今回の変更：＜例：5.1の読みを修正／BGMを減音＞
再生：＜確認用リンク＞　保存：＜WAVまたはMP4のリンク＞
期限：＜年月日・時刻・日本時間＞
確認してほしい点：
1. 00:03の「フェイブルごーてんいち」が自然か
2. 全体の速さと聞き取りやすさ
3. BGMが声を邪魔していないか
修正は「00:03、少しゆっくり」のように時刻付きでお願いします。
```

ユーザーの返答は対象版・時刻・採否とセットで記録する。短い声の採用を、別の回の完成動画全体の試聴済みへ拡大しない。担当者が試聴できない場合は、媒体検査だけを記録して「最終試聴未実施」と渡す。

## 11. 保存と再利用・GitHub

```text
outputs/productions/<案件ID>/voice-generations/<音声世代>/
  plan.json                       凍結した原稿・声・モデル・予定回数
  scene-00/Aoede/voice.wav         元の場面別音声
  scene-00/Aoede/request.json      キーを含まない生成条件
  scene-00/Aoede/submission.json   送信状態
  scene-00/Aoede/verified.json     hash・形式・時間・usage
  narration.wav                   連結した音声
  timings.json                    実音声の区間情報
  voice-source.json               編集へ渡す検証済み音声の参照
  listening-review.json           担当者が試聴結果を記録する例
```

最後の試聴記録ファイル名は今後の運用例であり、自動で生成されると保証しない。既存の別形式の試聴記録も参照元を明確にして使う。

引き継ぎには、WAVとともに案件ID、場面番号、表示原稿、読み原稿、voice、model、生成日、音声尺、sample rate、bytes、hash、変更点、試聴・採用状態を付ける。相対パスで素材を追跡し、ローカルの確認ページから最新版と旧版を開けるようにする。

**動画・音声の重い本体をGitHubへ保管する必要はない。** ローカルPCと必要な共有ストレージへ置く。GitHubにはこの手順、原稿、発音辞書、生成条件、改善理由、検証の要約を残す。キー、署名付きURL、個人情報入りログは入れない。共有リンクを再発行したら新しい期限を伝え、恒久的な素材台帳の代わりに使わない。
