# PC画面の撮影・公式画像の引用・人物との使い分け

作成日：2026-10-23。撮影担当者・編集担当者へ渡せる手順書。Windowsの実画面、公式サイトの製品画像・スクリーンショット、人物動画を解説に使う際の運用をまとめる。

## 1. 撮影する目的を先に決める

### 制作開始時に必ず実画面を確認する

2026-10-23のユーザー指示により、製品の解説を作るときは、台本・ナレーション・代替画像を固める前に、まずユーザーのPCで画面キャプチャを取得できるか調べる。

1. 対象アプリと開いているウィンドウを確認し、ログイン済みの環境で対象機能を探す。
2. 対象の文書や画面を実際に開く。既存の架空デモを優先し、一般の業務資料や個人情報を撮影題材にしない。
3. 撮影ツールで実画面を取得し、ファイルへ保存して開き直す。画面が開けたことと、保存できたことを分けて確認する。
4. 台本の主張を見せられるか、編集・コメント・前後比較など必要なカット、表示倍率と読める範囲を確認する。
5. 「撮影可能／一部のみ可能／未確認／撮影不可」、試した経路、理由、取得日、原本と公開候補の保存先を制作記録に残す。
6. 撮影できる箇所は実画面を優先して構成する。公式引用は機能の根拠や未提供機能の説明など、役割を決めて使う。撮影できない場合だけでなく、公式説明が必要な場面でも引用は併用できる。

既存の切り出しだけで説明を続けたり、公式説明のみへ置き換えたりする前に、この確認を行う。ログイン、権限、提供状況、読み込み不具合で止まった場合は実際に観測した状態を報告し、「このPCでは使えない」と一般化しない。

Claude Docsでは2026-10-23、ユーザーPCのClaude Desktopから既存の架空企画書を開き、文書全体、見出しと表、Commentsペイン、文章選択時のClaude編集ツールバーを撮影できた。今回の確認では本文を書き換えず、新しい修正依頼も送信していない。複数資料を使った作成や直接入力の実演は別途撮影する。

1カットで見せることを1つに絞る。「このボタンから書き出せる」「初回はこう出た」「修正で数字が変わっていない」「公式がこの機能を説明している」など、台本の説明と撮る対象を対応させる。

| 素材 | 伝えること | 残す記録 |
| --- | --- | --- |
| 自分のPCでの実演 | 実際に入力・出力・修正・書き出しできたこと | 製品、日時、操作、入力素材、初回と修正版、撮影原本 |
| 公式サイトの画面キャプチャ | 公式が説明する機能・条件・画面例 | URL、ページ名、確認日、引用箇所、表示条件 |
| 公式の製品画像 | 外観、UIの見た目、製品の位置づけ | 画像掲載元、製品・画像名、使用条件、取得日 |
| 人物動画・自作図解 | 困りごと、感情、理解の補助、次の行動 | キャラと素材のID、架空例であること、生成・編集条件 |

公式画像は自分の実証結果ではない。人物が喜んでいる演出だけで機能の成功を示さず、説明に必要な画面や結果を併せて見せる。

## 2. 撮影前にPCを整える

- 台本から対象の画面と操作を決め、架空の人物・店舗・企画データを用意する。
- アカウント名・メール・会話名・通知・個人ファイルが入り込まないようにする。不要な通知やウィンドウを閉じる。
- ウィンドウのサイズ、表示倍率、撮影する領域を決める。変更した設定はメモし、撮影後に戻す。
- 読ませる文字をアプリやブラウザー側で大きくする。撮影後に小さい文字を無理に拡大して使わない。
- アニメーション、画像、フォントが表示されるまで待つ。エラー画面や読み込み中を正常な結果として撮らない。
- 入力直前・初回出力直後を撮り、修正前の状態を失わないようにする。

## 3. Windowsで静止画を撮る方法

### 手動で撮影する

1. 対象のアプリ・ブラウザーを開き、必要な画面を表示する。
2. **Windowsキー＋Shift＋S** で範囲切り取りを開始する。必要に応じてウィンドウ単位または矩形を選ぶ。
3. 切り取った画像をSnipping Tool等で開き、PNGとして案件の撮影フォルダーへ保存する。クリップボードにあるだけで保存済みと扱わない。
4. ファイルを開き直し、文字、数値、切れ、解像度、余計な個人情報を確認する。
5. 撮影日時・製品・対象画面・元ページのURL等を同名のメタデータへ記録する。

Windowsキー＋PrintScreenで全画面を撮る方法もあるが、全画面には通知やアカウントが入りやすい。必要な撮影原本として残す場合は非公開領域へ置き、公開用の切り出しと分ける。保存先やPrintScreenの動作は環境設定で異なるので、実ファイルができたか確認する。

### 画面の動きを撮る

Snipping Toolの画面録画、またはプロジェクトで検証済みの画面収録機能を使い、対象領域、収録時間、マイク・PC音の有無を確認して録る。操作前の短い余白、クリックや入力、結果を読める時間、操作後の余白を残す。録画停止後は実ファイルを再生し、黒画面、通知、不要な発話、数値の切れを確認する。

静止画だけで十分な箇所を無理に録画しない。入力・修正の変化を示す箇所では、操作が分かる短い実録画を使う。人物の生成動画をPCの操作実証として扱わない。

### 自動で撮影する場合

その環境で利用できるComputerUse・スクリーンショット・ブラウザー撮影の正式な手順とツールを使う。ブラウザーのページ撮影と、Word／PowerPoint等のネイティブアプリ画面の撮影は別経路として記録する。撮れていない画面の内容を推測しない。画面の再作図をキャプチャの代わりにしない。

対象ウィンドウ・表示領域・保存先・取得方法を残し、保存後の画像を実際に確認する。全画面撮影が必須という意味ではなく、来歴と公開可能性の両方を満たす範囲で撮る。

## 4. 読める解像度で撮る

縦動画の中央に置く引用・実演画像は、実際の表示幅を先に決める。これまでの撮影では、約700px幅で表示する部分を、元画面で200%程度にして約1400px幅で撮る工夫を使った。これは事例であり、どの画面にも一律に同じ倍率を強制するものではない。

- ブラウザーのズームやアプリの表示倍率を使い、元画面で文字を大きくして撮る。
- 初回と修正後の比較は、同じ表示倍率・同じ領域で撮る。拡大率の差を改善効果と見せない。
- 同一領域を切り出し、元画像・切り出し座標・派生画像を追跡する。
- 画面全体では小さすぎる場合、必要な行、価格、日付、ボタン等を切り出す。前後関係を失う切り方をしない。
- UIや数字を生成AIで補完・再描画したり、文言を書き換えて、実画面として見せたりしない。
- PNGを基本とし、WebPを派生させる場合はlosslessを選び、必要に応じてデコード後の画素一致を確認する。JPEG原本をPNGへ変換しただけで画質が回復したとは説明しない。
- 最終的には360px程度のスマホ幅で、引用や実演の文字が読めるか確認する。画素数の検査だけで可読性に合格としない。

## 5. 公式サイトの製品画像・画面を引用する

1. 製品の公式サイト、公式ヘルプ、公式の発表・配布ページを優先して確認する。
2. 製品・機能・提供時期・地域・プランの条件を確認する。検索結果の見出しだけで決めない。
3. 動画で何を説明するために必要なのかを決め、該当画像・画面の箇所を選ぶ。
4. そのページや素材の使用条件、クレジット指定、再配布等の制約を確認する。**出典を書くだけで、すべての画像を自由に使えるとは扱わない。** 不明な素材は勝手に利用可とせず、別の説明方法を選ぶか確認事項として残す。
5. ページの画面を撮る場合は、掲載内容と引用箇所を確認し、必要な範囲をPNG等で保存する。公式の画像データを取得する場合は、掲載ページと画像の取得元を両方記録する。
6. 元画像・撮影原本を保全し、公開用の切り出しを別保存する。製品名、数値、機能の意味を変える加工をしない。
7. 動画の引用場面に「引用：OpenAI公式資料」「引用：Anthropic公式資料」等、見ている人が出所を分かる表示を置く。公式で確認していない画像へ公式クレジットを付けない。
8. 説明欄または `SOURCES_JA.md` にページ名・URL・確認日・使用箇所・関連する条件を記す。公式サイトの閲覧可能性と画像の利用条件は別に確認する。

公式のスクリーンショットを短い解説の根拠として見せる場合と、配布用の製品画像を素材として使う場合は、記録上も区別する。担当者が利用条件を判断できない場合は未確認とし、一般論だけで利用可と確定しない。

## 6. 実演と修正の撮影

同じ架空素材で、次の4段階を保存する。

1. 入力：何を依頼したか。
2. 初回出力：最初にどんなものができたか。
3. 修正依頼：どこをどう直したか。
4. 修正後：見た目・意味・金額・日付がどうなったか。

成功した最終画面だけでなく、初回と修正過程を残す。短くした文章の意味が変わった場合は、その変化も説明する。WordやPowerPoint等へ書き出したものは、可能なら実際のアプリで開き、取得したファイルと結び付けて撮る。外部アプリの画面を元製品の編集画面として表示しない。

## 7. 人物キャラを効果的に使う

人物は、見ている人が感情と仕事の流れを追える案内役として使う。最初に人物とペルソナをユーザーへ確認し、確認済み画像をMiniMaxで動かす。同じシリーズでは外見・衣装・役割・口調を保つ。

| 場面 | 人物の見せ方 | 画面と音声の役割 |
| --- | --- | --- |
| 冒頭 | 人物を全面に出し、困りごとの表情・手ぶりを見せる | 短い見出しで今回の課題。ナレーションで状況を補う |
| 試す場面 | 操作・初回出力へ切り替える | 実際の画面で何をしたかを見せる |
| 気づき | 人物の「ひらめいた」、納得、比較する動作を全面で見せる | 何が分かったのかを一言で示す。根拠は実画面や公式引用と結び付ける |
| 検証・比較 | 読ませる公式画面・結果・図解を優先する | 人物が重要な文字やボタンを隠さない |
| 締め | 同じ人物が落ち着いてうなずく・次の行動を示す | 今回の学びと次に試せること。次回へのつながり |

人物をただ大きく置くだけでなく、表情と動作に場面の意味を持たせる。考える、気づく、示す、締めるなど、同じ人物の複数の動作を使う。毎回同じ動作・同じ静止画の拡大だけで尺を埋めない。

見出しと字幕は顔を空けて置き、人物の目線や手の動きも確認する。人物素材の終了時刻を測り、足りない場面ではまとめ・別カットへつなぐ。ナレーションを途中で切らない。人物の外見や設定変更は版と理由を記録し、確認済みの人物像を無断で置き換えない。

## 8. 保存・出典・確認の記録

```text
outputs/productions/<案件ID>/<世代ID>/
  _private/captures/           非公開の撮影原本と文脈
  captures/original/           公開可能な原画像・撮影原本
  captures/public/             動画に使う切り出し
  captures/metadata.json       出典・日時・領域・加工・hash
  review/                      初回／修正後比較と確認画像
```

記録項目：素材ID、種類（公式／実演／自作）、製品、ページ名、URL、取得日時とタイムゾーン、使用条件、元ファイルのbytes・hash、切り出し座標、公開画像のbytes・hash、表示した出典、目視確認結果。

ユーザーへは「対象版」「今回の変更」「確認したい2〜3点」「再生・保存リンク」「期限」をまとめて伝える。文字の読みやすさ、引用と実演の区別、人物と重要画面が重ならないかを確認してもらう。撮影できたこと、読めること、ユーザーが採用したことは別に記録する。

重い録画・動画・音声原本はGitHub保管不要。GitHubへは撮影手順、出典、プロンプト、切り出し条件、改善理由、検証要約を残す。個人情報入り撮影原本と署名付きURLは公開しない。

## 9. 動画とブログで撮影素材を共用する

2026-10-23のユーザー方針により、動画の決定事項・実演画像・生成静止画・公式引用画像は記事にも活用する。[動画とブログの共通工程](VIDEO_TO_BLOG_WORKFLOW_JA.md) を参照する。

企画時に動画の短い表示範囲だけでなく、記事で操作や前後関係を読める範囲も撮る。原撮影は保持し、公開用に動画の縦切り出しとブログの横切り出しを分ける。動画の字幕を合成する前の画像を残す。撮影ツールがComputerUseであっても他の方法であっても、取得方法と条件を記録する。

記事では入力 → 初回出力 → 修正依頼 → 修正後を文脈とともに示す。公式画像には出典・確認日・何を示すかを添え、記事用途の利用条件を確認する。動画に使ったという理由だけで画像のブログ採用を確定しない。生成静止画は実画面の代替証拠にしない。

既存のClaude第1回の切り出しを確認すると横136〜432pxの画像があり、本文幅への拡大には不足する。原撮影からの広い切り出しか、拡大表示での追加撮影を検討する。受け渡しは公開用画像だけとし、個人情報入り原本や非公開proofをブログへコピーしない。
