# 動画からブログへつなぐ、自分用の制作環境

更新日：2026-10-25。ユーザーが示した方向性と現在の実装を分けて記録する。共通の画像照合・記事向け受け渡しはCLIで初期実装済み。2026-10-24に追加した企画管理の実装範囲は8節を参照。記事草稿の自動同期・ブログへの自動転送・公開は未実装。以下の同時進行は、このチャットの助手が既存ツールと記録を用いて行う制作上の必須工程であり、無人の自動実行を実装したという意味ではない。

## 1. 採用する方向性

製品の動画・記事を作る際は、最初にユーザーPCで対象機能のキャプチャを取得できるか確認する。実機で表示・保存・可読性を確認し、その結果から動画と記事の共通撮影計画を作る。公式説明や既存画像だけで構成を確定する前に、今回の主題に合う実画面を追加撮影できるか調べる。

まず自分が使いやすい制作環境へ磨く。1つのテーマについて、動画とブログを別々に準備する負担を減らす。共通の企画・検証・素材から、短い解説動画と詳しい記事を作る。

当面はこのチャットを制作窓口にする。記事個別の調整を行いつつ、繰り返し使う処理はStudioへ随時追加する。ユーザーがStudioを操作することを工程の前提にしない。レビュー動画はGoogle Driveへ版付きで保存し、モバイルから見られることを優先する。S3はDriveが難しい場合、または会社への持ち込みに指定された場合の代替とし、自動で二重送信しない。

- 動画：困りごと、試した結果、変化、詳しく読む理由を短く伝える。
- ブログ：前提条件、操作手順、入力例、初回出力、修正依頼、修正後、注意点、公式根拠を読める形で残す。
- 共通：読者、伝える結論、確認した事実、出典と確認日、架空の実演素材、人物設定、画像原本、採用・修正理由。

ブログをナレーションの文字起こしだけにしない。動画を見た人が「自分でも試せる」「画面や数字を見比べられる」ことを記事の役割にする。動画と記事は1対1に固定せず、複数のショートを1本の詳細記事へ結び付けてもよい。

### 投稿先と中心テーマ（2026-10-25追加）

記事の既定の投稿先はユーザーの `benriworks/blog` リポジトリとし、案件によってnoteも選ぶ。中心テーマはClaude・ChatGPT・Codexの機能、使い方、実演、比較、関連ニュース。これは題材の重点であり、PHPなどユーザーが指定した他のテーマを中止・除外する規則ではない。

投稿先の指定がなければblogを前提に草稿と素材を準備し、毎回の選択をユーザーに求めない。note指定へ変わっても再調査・撮影を最初からやり直さず、共通草稿・出典・原素材を再利用する。企画・レビュー記録には投稿先（blog／note／未定）、決定の根拠、媒体別の草稿版・画像・公開状態を残す。以下で「ブログ用」「記事用」と記した素材収集・解像度・出典・個人情報の規則はnote向けにも適用する。

| 投稿先 | 媒体に合わせる作業 |
| --- | --- |
| blog（既定） | リポジトリのAGENTS.md・画像規定に従い、MDXと画像配置へ変換してdraftで確認する |
| note | 共通草稿から見出し・本文・画像順・キャプション・出典リンクを整える。blog固有のMDXコンポーネントや画像パスを本文へ持ち込まず、実際の編集・プレビュー環境で可読性を確認する。未確認の表示機能を利用できると断定しない |

レビューには対象媒体を明記する。動画からの記事誘導も実際の投稿先と公開済みURLに合わせる。blogとnoteへの二重投稿は既定にせず、媒体の指定を投稿・公開の承認と混同しない。4節のリポジトリ配置・mainマージの手順はblogの場合に適用し、noteでは草稿保存・レビュー・公開を別に記録する。noteへの自動投稿機能を追加したものではない。

### 実演より先に、伝える価値を決める

企画には「見終えた人に残す一文」「従来もできたこととの関係」「その価値を見せる画面」を残す。操作が成功しても、一般的な文書生成の例だけではDocsを紹介したことにならない。製品の機能説明、利点の解釈、実際に検証したことを分ける。2026-10-23のDocsレビューでは、数字の照合に寄ったv01から、同じ文書を人とClaudeで仕上げる流れへ構成を改めた。

### 動画制作と記事準備を同時に進める（2026-10-25必須化）

今後の動画制作では、別途の記事作成依頼を待たず、同じ案件IDで記事草稿と掲載候補素材を準備する。作業再開中の案件にも以後の工程から適用する。過去の全案件の再撮影・再制作を一括で始める指示ではない。

| 動画の工程 | 同時に進める記事準備 | 保存・確認するもの |
| --- | --- | --- |
| 調査・構成 | 読者、中心メッセージ、具体例、詳しく説明する仕組み、前提・注意点を草稿化 | 記事の仮題・本文、主張と出典の対応、確認日、未確認事項 |
| 公式情報の確認 | 引用に必要な公式HPの画面と短い引用候補を確保 | ページ名・URL・取得日・引用原文と範囲・自作要約の区別・利用条件・掲載理由 |
| 実機確認・撮影 | 記事で手順と結果を読める範囲を動画用と一緒に撮る | アプリと環境、入力・初回出力・修正前後、保存した原本・寸法・倍率・hash |
| 編集・改訂 | 決めた内容、図解・人物・生成静止画の適切な記事用途を反映 | 動画場面と記事節の対応、素材ID、版、出典変更時の要確認箇所 |
| 動画レビュー | 記事草稿と画像候補も一覧で提示 | 各ファイルの保存先、取得済み／不足／該当なし、記事だけで補う内容、確認事項 |

記事草稿は見出し一覧やナレーションの転記で終わらせず、導入・要点・具体例・仕組み・対象条件・手順や確認先・出典を本文で用意する。未確認の操作・結果・公開日を創作しない。ブログへの実ファイル配置時はブログ側のAGENTS.mdと画像規定を読み、draftとして扱う。

記事画像は、実際の本文表示幅の約2倍の原本を撮影時に確保することを目安とする。表示幅700pxなら約1400px。画素数だけで合格とせず、PC本文幅と360px程度のスマホ幅で実際に読む。広い画面は全体と必要箇所の詳細を組にし、撮影倍率と領域を記録する。環境上目標寸法を得られなければ、適切な拡大表示・別カットでの再撮影を試し、残る不足を記録する。小さい動画用切り出しの引き伸ばしや完成MP4からの抜き出しだけで、記事用原本の準備完了としない。

アプリ撮影は架空素材だけを用いる。主題に実演するアプリがなければ理由付きで「該当なし」、入口や保存を確認できなければ「未確認／撮影不可」とし、試した経路・理由・代替・残作業を残す。未取得を図解で埋めても実画面の取得済みへ変更しない。公式ページも未取得・利用条件未確認の素材を掲載可能と断定しない。

軽量な草稿は `productions/content-projects/<id>/article-draft-vNN.md`、出典は `SOURCES_JA.md` または案件の出典台帳へ保存する。これは今後の命名規則であり、各案件にそのファイルが既にあるという意味ではない。原本と公開用切り出しは既存の撮影ルールで分離し、記事候補画像は `outputs/content-projects/<id>/blog-handoff/<version>/assets/`、寸法・hash・出自・使用先・確認状態は同世代の `asset-manifest.json` からたどれるようにする。旧版を上書きせず、非公開原本は受け渡しへ混ぜない。

動画レビューの際は「動画」「記事草稿」「記事画像・公式引用一覧」「不足と次の作業」をセットで案内する。動画単体を先に見せる場合も記事の進捗を明記し、未完成の草稿・素材を納品済みとしない。記事草稿と素材収集は通常の制作範囲に含めるが、ブログ公開・mainへのマージ・YouTube公開は別の明示的な依頼に基づく。動画承認を記事公開の承認に読み替えない。

## 2. 1つのコンテンツ案件から2つの成果物を作る

`content_project_id` を動画ID・記事slugより上位の共通IDにする。既存のproduction IDや素材パスは変えず、参照で結び付ける。記載例は [content-project.example.json](templates/content-project.example.json)。これは将来の契約案であり、StudioのDBスキーマではない。

| 共通の記録 | 残す内容 | 更新したときの対応 |
| --- | --- | --- |
| 企画 | 読者、課題、結論、試してほしいこと | 動画見出しと記事構成の両方を見直す |
| 事実・実証 | 主張、公式根拠／実演の区別、確認日、製品・条件 | どの場面と記事節が使っているかを確認する |
| 人物 | キャラID、承認範囲、仕事・困りごと・気づき | シリーズの一貫性と記事内の役割を確認する |
| 素材 | ID、原本、派生元、用途、寸法、hash、出典 | 古い派生を勝手に差し替えず、改訂として残す |
| レビュー | 技術検証、AI補助確認、試聴、ユーザー採用、公開 | 動画とブログで別々に記録する |
| 導線 | YouTube URL、記事の公開URL、案内文 | 予定URLと公開済みURLを区別し、リンクを確認する |

映像が完成してから素材を探し直す運用を減らす。企画時点で「動画ではここを見せる／記事ではこの操作と前後を載せる」を決め、撮影と出典調査を共通で行う。

## 3. 画像を再利用するときのルール

| 素材 | ブログでの使い方 | 残す記録・確認 |
| --- | --- | --- |
| ComputerUse等で撮影した実演画面 | 手順、入力、初回出力、修正前後を示す | 製品、操作日時、架空素材、操作・取得条件、原撮影への参照、個人情報の除外 |
| 生成した静止画 | 人物の場面、概念や仕事の状況を補う | 生成方法、プロンプト、人物版、参照画像、実画面ではないこと、採用範囲 |
| MiniMaxの人物動画 | 動画では動作と感情を見せる。記事では必要な静止画原本または意味のある代表カットを使う | 承認済み人物との対応、どの場面の画像か、元動画と時刻。毎回同じ装飾を増やさない |
| 公式サイトの製品画像・画面キャプチャ | 解説の根拠となる箇所を本文とともに示す | 公式URL、ページ名、取得・確認日、必要な範囲、加工内容、利用条件・掲載目的の確認 |

出典を付けただけでどの画像でも掲載できるとは扱わない。公式素材はブログでの利用条件と必要性を改めて確認する。第三者の顔写真や一般の広報写真を、製品の画面であるかのように使わない。外部画像の直リンクに依存しない。

動画への採用・技術検証は、ブログへの採用や公開の承認を兼ねない。画像ごとに `channels.video` と `channels.blog` の状態を持つ。初回出力を修正後として掲載したり、生成した画面を実演の証拠として掲載したりしない。

### 原本を共有し、表示用は媒体に合わせる

- 字幕や大見出しを重ねる前の画像を残す。完成MP4のフレームだけを画像原本にしない。
- 動画用の縦切り出しと、記事で操作が読める横切り出しを同じ原撮影から作る。意味のある前後関係や製品の識別を消さない。
- ブログの本文表示幅に合わせる。現行ブログの約700px表示なら、可能なら約1400pxの撮影原本を確保する。実際の本文幅・スマホ表示で読めるかを確認する。
- 小さい既存切り出しを無理に拡大しない。文字をAIで描き直したり、補間で細部が復元したと説明したりしない。原撮影の再確認または追加撮影を行う。
- キャプションは何を確認できる画面かを説明し、公式画像なら出典・確認日を添える。altは画像の意味を伝え、キャプションの丸写しだけにしない。

## 4. 現行ブログへの受け渡し

確認対象：`benriworks/blog` のローカル実装（2026-10-23）。既存ブログの `AGENTS.md` とビジュアル規定を作業直前に読み直す。

- 記事は `content/articles/<slug>.mdx`、手順中心なら `content/guides/<slug>.mdx`。画像は `public/images/articles/<slug>/` に安定したファイルとして置く。
- `Figure` で `src="/images/articles/<slug>/..."`、alt、キャプション、寸法を指定できる。`/blog` は表示側が付けるため、画像srcへ重ねて付けない。
- 現行サイトの公開基点は `https://benriwork.jp/blog`。記事URLは種別とslugから決めるが、未公開の予定URLを公開済みとして案内しない。
- YouTubeへの参照は現行の外部リンク／`Cta`で扱える。動画埋め込み専用コンポーネントは確認した許可一覧にはないため、埋め込みを実装済みとはしない。
- S3の期限付きレビューURLを、記事画像や恒久的な動画導線として使わない。ブログ用画像はブログ側へ明示的にコピーし、元素材のhashと受け渡し先を記録する。
- 動画の人物と、ブログ全体の既存案内役は別の人物設定。シリーズの登場人物を記事にも使う場合は、現行の「1記事1人」等の規定との整合を確認し、サイト全体の案内役を無断で置き換えない。

記事作業の流れは、読者・目的と構成の確認 → `draft: true` の原稿 → 内容・画像・リンク検証 → draft PR → 人による確認 → 公開。現行ブログではmainへのマージが公開操作になる。無関係な未コミット作業を巻き込まず、必要なら別の作業場所を使う。

## 5. YouTubeからブログへの導線

2026-10-23にYouTube公式ヘルプを確認。**ショートの説明欄とコメントに書くURLはクリックできない。プロフィールのリンクはクリックできる。** そのため、最初は次の案内を基本とする。

```text
ショートの締め：手順と入力例は、プロフィールのブログへ。
チャンネルのプロフィール：公開済みの動画連動記事、または記事を探せる入口。
ブログ：今回の要点 → 手順・入力例 → 実画面と前後比較 → 条件・公式出典。
記事内：対応する公開済みYouTube動画へのリンク。
```

複数の記事が増えたら「動画から来た方向けの入口」を作る案を検討する。現時点でそのページが存在するとは扱わない。まずは公開済み記事へ直接つなぐ方法で試せる。

ショートの「関連動画」は自分のチャンネル内の動画・ショート・ライブへ付ける機能で、ブログへの外部リンクの代わりにはならない。必要なら詳しい長尺動画を経由するが、経路を作るためだけに新規動画制作を増やさない。

公式根拠：

- [視聴者にリンクを共有する方法](https://support.google.com/youtube/answer/13748639?hl=en-GB)
- [ショート動画に関連動画を追加する](https://support.google.com/youtube/answer/14075157?hl=en)
- [チャンネルのプロフィールを管理する](https://support.google.com/youtube/answer/2657964?hl=en)

## 6. ローカルで迷わずレビューできる保存案

```text
productions/content-projects/<content-project-id>/
  content-project.json          企画・事実・出典・素材ID・動画と記事への参照
  article-brief.md              読者・構成案・動画からの追加価値
  review-record.md              動画と記事の指摘・採否・公開判断
outputs/content-projects/<content-project-id>/blog-handoff/<generation-id>/
  assets/                      受け渡し候補の公開用画像だけ
  asset-manifest.json          元素材・hash・寸法・記事用途・追加作業
  review/index.html            画像と説明をまとめて確認する入口
  verification.json            コピー照合・画像確認の実施範囲
```

これは今後の保存案。既存素材は大量移動せず参照を残す。GitHubには軽量な企画・台帳・手順・修正理由を残す。動画本体・音声・非公開原本・署名URLを入れない。公開するブログ画像は、必要な対象を選び、ブログリポジトリ側の規定で管理する。

レビュー依頼は「動画ID／記事案／画像候補の版」「動画と記事で伝えること」「見てほしい点2〜3個」「追加撮影が必要な箇所」「PCでの確認入口／必要ならスマホ共有」をセットで示す。画像確認・記事採用・公開判断を区別する。

## 7. 小さく確認してから仕組みにする

1. **今回の準備**：方向性、共通記録のひな形、既存素材の再利用候補を残す。アプリ機能の実装とは区別する。
2. **最初の1組の候補**：既存の「ClaudeでメモからDocsの下書きと修正」の動画を使い、入力 → 初回 → 修正 → 照合を記事にする。動画の最終台本と実証記録を照合し、古い出典メモの「未取得」等を現在の状態と混ぜない。
3. **動画制作と並行**：記事草稿と広い画面・公式引用候補を準備し、不足はその時点で記録する。記事構成の修正に応じて必要な箇所だけ追加撮影し、ブログ側への受け渡しはdraft PRで確認する。2026-10-25以降、記事構成の別途確認を素材収集の開始条件にしない。再撮影・記事作成・投稿は文書の更新だけで完了したとはしない。
4. **制作と並行する共通化**：`tools/studio/content_projects.py` に、公開用画像のhash・寸法・出自・確認状態の照合、版付きコピー、素材台帳とFigure記述の出力を追加した。チャットからCLIを利用できる。Studioの画面・APIからの登録、Drive自動アップロードは未実装。制作中の共通課題を記録し、機能を随時追加する。

最初の評価項目は、素材を探し直す手間、撮り直しの理由、動画と記事の説明の一致、スマホで画面が読めること、プロフィールから記事へ到達できること。閲覧や流入の数値は取得してから記録する。

## 8. 2026-10-24 共通企画管理の実装

上記7節の初期段階を拡張し、[企画ワークスペース](../../STUDIO_CONTENT_WORKSPACE_JA.md) にCLI・API・Studio確認画面を追加した。助手が調査→本数と概要を提案→ユーザーの意図を反映→採用構成を記録→撮影・根拠・素材・絵コンテを結ぶ。ユーザーにStudio操作を求めない。

現在の正本はSQLite内の版付き企画。旧JSONは元状態のまま取り込み、当時の「未取得」と現在の撮影記録を勝手に同一視しない。記事節にepisode_ids/claim_ids/asset_ids等を持たせ、変更の影響を受ける節だけ再確認する。公開画像の検証・コピーには既存の受け渡し処理を使う。記事原稿の自動同期・Drive自動送信・公開は引き続き未実装。
